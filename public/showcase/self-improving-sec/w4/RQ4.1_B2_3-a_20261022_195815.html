摘要

本报告基于知识图谱中 256 个 metric、402 个 problem、385 个 method、141 篇 paper、235 个 dataset、226 个 limitation 与 100 个 assumption 节点及其关系边，系统分析了 RQ4.1：通用指标与安全专用 oracle 的构成比例，以及「security-specific oracle 缺席」在实践中被哪些 proxy 指标替代、带来何种系统性偏差。核心结论是：安全专用 oracle 在 KG 中并非「少数派」而是**结构性空缺**——可执行验证类指标（per-sample label agreement、scanners-agree filtered samples、verification success）均仅被单篇论文使用，无一成为 ≥3 篇论文的共用 repair 评估口径；社区实际用 compile rate、plausible patches、EM、CodeBLEU、静态扫描安全率等 proxy 拼出评估替代物。

这些 proxy 带来四类系统性偏差：聚合指标掩盖逐样本错误 [1]、静态扫描器在定义层面覆盖残缺（6/18 类漏洞不可表达为静态规则）[2]、对真实改进不敏感且可被删代码游戏化 [3]、功能保持无法被验证而退化为相似度代理 [4]。对抗条件下整套 proxy 组合进一步全面失效：>90% 对抗 bug report 可诱导出攻击者意图的 patch，而最佳过滤器仅拦下 47% [5]。

数据来源与规模

分析完全基于知识图谱的结构化数据，共执行 41 次工具调用，覆盖全部六类核心节点：metric（256）、problem（402）、method（385）、paper（141）、datasetbenchmark（235）、limitation（226）与 assumptionconstraint（100）。对每个被引用论文，均通过 get_relation 拉取其完整一跳关系边（proposes/addresses/measured_by/evaluated_on/has_limitation/extends/compares_with/supports），并从边的 evidence 字段提取论文原始语句作为引证依据。

深入分析的论文共 16 篇，重点核查对象包括：指标批判类 [3]、静态扫描器可靠性类 [1][2][6]、对抗效度类 [5][7]、安全修复评估实践类 [8][9][10]、执行式 oracle 修正方向 [11][12]、元评估框架类 [13][14]、安全指标合法性审查类 [15]。

核心分析一：静态分析器被当作安全 oracle 的系统性偏差

这是 KG 中被最多论文共同指向的偏差源，也是「oracle 缺席后被 proxy 顶替」最典型的环节。前序文献普遍假设「静态分析工具输出可靠反映代码安全，无需人工验证」，KG 中该假设被显式建模为一条 assumptionconstraint 节点，而 [1] 用 1,080 条人工标注样本直接证伪它：CodeQL 与 Semgrep 的聚合安全率相近（人类 61%、Semgrep 60%、CodeQL 80%），但逐样本标签一致性只有 Semgrep 65%、CodeQL 61%——**聚合指标掩盖了逐样本的系统性偏差**，这是「用扫描器当 oracle」最致命的认识论错误。

[2] 给出更极端的覆盖率证据：面对 46 处从上游修复中挖掘的已知弱点位置，CodeQL、Semgrep、Clang 全部命中 0 处，cppcheck 仅命中 1 处，而 LLM 条件最多回收 76%；更关键的是，其 18 类漏洞分类中有 6 类**根本无法表达为静态分析规则**——静态 oracle 在定义层面就覆盖不到部分漏洞类型，这不是精度问题而是可表达性问题。[6] 作为使用扫描器做评估的原始论文自身承认「安全评估依赖 Semgrep 和 CodeQL，二者存在假阳/假阴」。

核心分析二：compile rate 类 proxy 的偏差结构

[3] 用五个受控实验（E1–E5，203 个 Big-Vul 单函数、三个开源代码 LLM）系统拆解了 compile rate 的五种失效模式，这是本 RQ 关于「proxy 替代带来什么系统性偏差」最完整的实证答案：

(1) **对真实改进不敏感**——compile rate 不响应那些合理改变输出质量的干预；(2) **失败误归因**——多数编译失败反映的是评估环境缺失（缺项目上下文、工具链）而非模型能力；(3) **配置依赖**——单一编译 flag 即可让 compile rate 波动达 2.7 倍；(4) **与其他指标反向**——compile rate 与 CodeBLEU 对模型给出完全相反的排名；(5) **可游戏化**——优化 compile rate 会奖励代码删除与退化补丁，且现有 change-aware screen 对退化补丁仍给出 0.08–0.48 的非零分数。作者提出的 diff_F1 也仅被定位为「文本编辑重叠代理」，自承未做人工标注相关性研究、对 deletion-style 补丁非近零给分。

换言之，社区在发现 compile rate 失效后，用 diff_F1 替换——但**替换的仍是 proxy，oracle 依旧缺位**。这是「proxy 换 proxy」的典型闭环。 [3] 的 limitation 节点直接写明：「既非 compile rate 也非 diff_F1 能验证漏洞已被移除或行为已被保持」，且「没有任何结论基于静态分析输出」。

核心分析三：功能保持度量的缺失与「proxy 叠 proxy」链条

安全修复必须同时保证漏洞消除与功能保持，但 KG 显示功能保持几乎完全依靠 proxy：compilable patches（编译通过）或项目测试套件通过。 [3] 证明这两者都不足以验证行为保持。更直接的证据来自 [4]：CodeGuarder 明确承认其 Sim 指标「衡量代码与参考实现的相似度，但因 CyberSecEval 数据集缺少测试用例，无法直接评估功能正确性」——在缺少执行式测试的情况下，功能保持度量退化为**代码相似度**，而相似度与功能正确性之间并无保证关系。这形成了一条「proxy 叠 proxy」的链条：安全用扫描器判（不精确）→ 功能用相似度判（无测试支撑）→ 两者都非 oracle。

值得注意的是，[11] 代表了修正方向：CodeSecEval 引入执行式 security tests，并拆分出 Function-Pass@1（只过功能测试）、Secure-Pass@1（只过漏洞定向安全测试）与 Pass@1（两者皆过）三个互补指标——这是 KG 中少见的、把「功能保持」与「安全达成」显式分离并各自执行验证的设计。但其本身尚未成为社区口径，且 [11] 自承现有部分基准缺乏综合安全测试（其 addresses 的问题节点即「基准中安全评估不足」）。

核心分析四：对抗条件下的评估效度全面失效

「功能测试通过 + 静态扫描干净」这套 proxy 组合在对抗条件下系统性失效，是效度威胁最严重的一类。 [5] 在五个 SWE-bench Python 仓库上构造 STRIDE 威胁模型下的五类攻击模式（Noise/Naive/Injection/Revert-CVE/CI-CD），发现 **>90% 精心构造的对抗 bug report 使 LLM APR 产出符合攻击者意图的 patch**，而最佳前置过滤器只拦下 47%、项目测试套件几乎检测不到、防御常常静默失败。

[7] 将这一威胁模型扩展为模型无关的 SWEADV 基准（750 条对抗 issue，5 类攻击，源自 SWE-bench Verified），发现**所有被测 APR agent 都产生「功能正确但不安全」的 patch**，且 LLM-as-judge、patch 级检测与组合检测均不足。这两篇论文共同说明：当攻击者主动利用评估盲区时，proxy 指标不仅「不够准」，而是会给出与安全事实相反的绿灯信号。这直接构成对「自改进结果可信度」的核心威胁——自改进循环若以 proxy 为奖励信号，会把「通过测试但引入后门」的行为当作改进固化下来。

核心分析五：安全指标自身的合法性审查与元评估缺口

即便指标「安全专用」，也不等于合法。 [15] NAAMSE 指出：只优化攻击成功率会让模型以「一概拒答」骗过安全分，从而损害可用性——因此安全评估必须同时约束 benign-use correctness，形成效用-安全权衡；该文同时自承「依赖 LLM judge 引入偏差与方差」。这提示对共识指标的对抗性审查是双向的：既要审查通用 proxy 是否度量了核心属性，也要审查安全专用指标是否可被 degenerate 策略欺骗。

[13] 的元评估框架从另一侧补全了缺口认识：它把 false_recovery（错误宣称已恢复）、time_to_recovery、degradation_area、detection_delay、retention、transfer 等设为评估协议的核心 metric，并明确要求「恢复声明必须说明其作用域」；[14] 对应地指出「局部遏制证明事件被阻止，但生命周期恢复需要关于该状态后续激活的证据」，且「所选研究在激活与暴露覆盖上较强，但在后代修复与可争议性上证据较弱」。 [13] 自承是无新基准结果的概念性贡献——这恰恰说明：领域**已经识别出**缺少可验证修复/恢复证据这一结构性缺口，却尚未把它落成被广泛采用的度量。

核心分析六：评估不可比性审计

同一「repair success」标签下的数字不可直接比较，这一点必须在结论中突出强调。KG 显示各论文的评估对象在规模、语言、粒度上差异巨大：[3] 在 203 个 Big-Vul C/C++ 单函数上做函数级修复；[10] 在 ARVO 5,001 个真实 C/C++ 漏洞（采样 588 个）上做项目级修复；[5] 只在 5 个 SWE-bench Python 仓库上评估；[9] 在 PrimeVul 5,480 对 C/C++ 与 Java X1 数据集上以 EM 为主指标；[8] 在 ExtractFix 10 个 CVE 与 VjBench/Vul4j Java 集上报告 plausible/compilable patches。这些设定下的「成功率」不可通约。

指标异质性进一步加剧不可比：同一概念在不同论文中定义不一致——例如 Pass@1 在 [4] 中是「top-1 生成解通过测试」，在 [18] 中是「生成代码非漏洞比例」，在 [19] 中是「隐藏单测通过比例」；security rate 在 [20] 中由 CodeQL 判定，在 [18] 中为「非漏洞代码占比」。按任务类型分组后，repair 组的指标集合 Jaccard 相似度偏低（compilable/plausible/EM/diff_F1/repair success rate 混杂），detection 组相对收敛（Accuracy/Precision/Recall/F1 为主，但 K 值与阈值定义不一）。这提示：检测类任务的评估已部分收敛，而修复类任务的评估仍高度碎片化，尚未就「什么叫修好了」达成共识。

核心分析七：构成比例的判读与修正方向

关于 RQ 的构成比例问题，KG 数据支持一个定性但可靠的判断：通用/代理指标是评估主体，安全专用 oracle 是**结构性缺席**而非「少数派」。命题中给出的通用指标（Accuracy 10、Recall 8、Pass@1 6、Precision 6、F1 5）合计 35 条 measured_by 关联；而可执行 oracle 类指标（per-sample label agreement、scanners-agree samples、verification success、known weakness recovery、detection rate via fuzzing）在 KG 中分别只被 1 篇论文使用，唯一接近共识的是「detection rate（fuzzing 复现口径）」被 [12] 与 [5] 两篇使用——仍未达 3 篇阈值。

需要修正的方向已在 KG 中显现：[11] 用执行式 security tests 拆分 Pass@1/Function-Pass@1/Secure-Pass@1；[12] 坚持「每个报告的漏洞都必须可复现」（fuzzing 复现为确认条件）；[2] 提出「LLM/静态分析器的发现在被 fuzzing harness 复现出 sanitizer 故障之前只是假设」；[13] 把 false_recovery 等纳入评估协议。这些共同指向「执行式 oracle」范式，与主流 proxy 实践构成方法论对立，但尚未形成共识口径，且各有局限（[11] 受限于数据集是否有测试、[12] 假设单输入 fuzzing 模型）。

分析局限性

**数据覆盖不足**：KG 中大量 method 节点的 origin_paper_id 为空（如 RAG pipeline、prompt-only baseline、compiler-feedback loop 等方法节点），导致无法完整还原每篇论文的指标全集合；measured_by 边也只记录了论文显式声明的核心指标，遗漏次要指标。因此「安全专用 oracle 占比」只能作「结构性缺席」的定性判断与可核查的局部计数，不能给出严格百分比，报告中的构成比数字应视为下界估计。

**原文溯源降级**：本环境未注册 RAG 原文检索工具（search_paper_sections 多次调用返回 unknown tool），无法逐句核实 Section 级原文与语义相似度分值。本报告所有引证取自 KG 边 evidence 字段中的论文抽取语句，可视为二级原文证据（verbatim quote 但未经原文复核）。建议下游在正式写入综述前，对 [1][2][3][5][7] 五篇核心论文做原文抽查。

**推断性判断标注**：C10 关于 [9] VulKey 以 EM 为主指标存在效度问题的判断，原文未明确讨论 EM 对漏洞消除的效度，属分析者推断；C8 关于 [13] 填补 oracle 维度的判断亦基于概念对照而非实证。两者均标注为中等置信。 [2] 关于静态扫描器覆盖率残缺的结论基于 Autoware 单一代码库，跨域泛化性待验证。

结论

RQ4.1 的答案是：256 个 metric 中，通用与代理指标构成评估主体，而安全专用 oracle 是**本体层面的结构性缺席**——可执行验证类指标（per-sample label agreement、scanners-agree samples、verification success）均仅被单篇论文使用，无一达到「≥3 篇论文共用」的共识门槛。社区用 compile rate、plausible patches、EM、CodeBLEU、静态扫描安全率、代码相似度等 proxy 拼出一套「看起来像评估」的替代物。

这些替代带来五重系统性偏差：(1) 聚合指标掩盖逐样本错误——CodeQL/Semgrep 逐样本一致性仅 61%/65%，尽管聚合安全率相近 [1]；(2) 静态 oracle 覆盖率残缺且存在定义盲区——46 处已知弱点静态扫描器几乎全错过，6/18 类漏洞不可表达为静态规则 [2]；(3) 对真实改进不敏感且可被游戏化——compile rate 在单一 flag 下波动 2.7 倍，删代码仍得分 [3]；(4) 功能保持无法验证——退化为相似度代理，构成 proxy 叠 proxy 链条 [4]；(5) 对抗条件下全面失效——>90% 对抗 issue 成功诱导不安全 patch，所有被测 APR agent 均产「功能正确但不安全」的 patch [5][7]。

这一评估框架的结构性缺口已产生可观测后果：领域已识别「缺少可验证修复/恢复证据」的问题（[13] 把 false_recovery 纳入评估协议），但尚未落成广泛采用的度量。修正方向（执行式 oracle：[11] CodeSecEval 的 Function/Secure-Pass@1 分离、[12] fuzzing 复现确认、[2] 假设须经复现验证）与主流 proxy 实践构成方法论对立，但均未成共识且各有限制。对自改进结果可信度的最终含义是：若自改进循环以 proxy 为奖励信号，系统会把「通过测试但引入后门」的行为当作改进固化——这正是 RQ4 层面最核心的效度威胁。此外必须强调，不同论文的「repair success」数字因数据集、语言、粒度与指标定义差异而不可通约，任何跨论文数值比较在方法学上均不成立。
