摘要

本报告围绕 RQ2.2 展开：程序运行反馈（崩溃复现、测试执行结果、动态分析/sanitizer 信号）与测试覆盖率信号（code coverage）分别贡献多少可测改进，以及覆盖率作为自改进驱动是否被系统性低估。核心结论是：两类信号的可测贡献呈现鲜明不对称——程序运行反馈作为自改进驱动的直接有效性被大量工作反复验证，证据链宽而实（如 AutoSafeCoder 静态分析反馈四轮内修复 53% 漏洞 [1]，VRpilot 把编译器/sanitizer/测试套件三类执行信号作为 patch 验证反馈底座 [2]）；而覆盖率信号在 KG 的 256 个 Metric 中仅有 3 篇论文以 code coverage 度量支持，处于支持度靠后位置。

本文判断覆盖率确实被系统性低估，但根源不在其弱，而在评估体系偏好离散「正确/可复现」指标、覆盖率需长链路兑现且度量命名碎片化（code/branch/edge/instruction coverage 分立），使其支持度被统计性压低。CovRL 用 TF-IDF 覆盖图 + PPO 发现 48 个真实 bug（含 11 个 CVE）[3]、FUEL 以覆盖率驱动多种反馈发现漏洞 [4]，单位证据强度并不低。最大的证据缺口在于缺少统一 benchmark 上两类信号的 head-to-head 消融，故本 RQ 判定为「部分回答」。

数据来源与规模

本分析基于父问题 RQ2 冻结证据矩阵中的核心论文（AutoSafeCoder [1]、FUEL [4]、deepSURF [6]、PAGENT [5]、CovRL [3]），并沿知识图谱的一跳/二跳关系扩展到其上下游谱系（LLAMA [7]、LLM4FUZZ [8]、ELFUZZ [9]、语义混合 fuzzing [10]、SAFuzz [11]、VRpilot [2]、end-to-end secure code [12] 等），共精读约 15 篇论文的节点与关系数据。工具侧共加载 KG 的 metric、problem、limitation、assumption、method、dataset 等多类节点，其中 metric 总量 256 个、problem 402 个、method 385 个、limitation 226 个、assumption 100 个（均为 KG 全量计数，本次检索为分页取样）。核心信号的支持度通过 measured_by 边的反向追溯精确还原，覆盖率家族（code/branch/edge/instruction）分别定位到具体论文。

主线一：程序运行反馈——证据链宽而实，但多为间接贡献

程序执行反馈的有效性有多条量化证据支撑。AutoSafeCoder [1] 的 Static Analyzer Agent 在最多四轮迭代内修复了 53% 的漏洞，相较 LLM 基线实现 13% 漏洞下降；但其 Fuzzing Agent（崩溃检测通道）仅处理了 65 个样本，并受不兼容依赖与权限管理问题困扰，说明崩溃反馈通道存在、但贡献信号被工程实现稀释。VRpilot [2] 系统性地把编译器报错、sanitizer、测试套件三类执行信号作为 patch 迭代反馈，并成为后续 RAVEN、MemRepair、EvoRepair、KEAREPAIR、EviRepair 等 15+ 篇工作共同继承的「patch 验证反馈」范式底座 [2]，这本身就是该信号强有效性的社群级背书。PAGENT [5] 用 sanitizer 插桩二进制的崩溃信息（non-zero exit code）作为精修反馈，其 PoC 成功率直接以「触发 crash」度量。deepSURF [6] 则以 AFL++ + ASan 检出 42 个内存破坏 bug（含 12 个此前未知）。

值得注意的是，程序执行反馈的高支持度部分源于「易测量性」：crash/test 是天然离散、易在 benchmark 报告的终局指标，因而被更频繁地当作评价口径，这构成下述覆盖率被低估的对照背景。

主线二：覆盖率信号——篇目少，但单位证据强度不低

覆盖率作为自改进驱动的最高强度单点证据来自 CovRL [3]：它通过 TF-IDF 加权覆盖图配合 PPO 微调，把覆盖率反馈注入 LLM 变异器，在四个 JS 引擎上均超越 SOTA，并发现 48 个真实 bug（39 个新、11 个 CVE）[3]。它所对标的问题节点正是「现有 LLM fuzzing 仅黑盒式使用覆盖率引导」。FUEL [4] 把多种执行反馈转化为分析摘要驱动生成，并以 code coverage、valid test ratio、number of bugs 三指标度量，其对标的问题即「多数 LLM fuzzer 不利用语义丰富的执行反馈，导致覆盖率下降与漏检」[4]；LLAMA [7] 作为 FUEL 的扩展把反馈驱动多目标变异移植到智能合约 [7]。

关键发现是：覆盖率信号家族的实际覆盖比「code coverage 3 篇」更广。branch coverage 由 LLAMA 使用 [7]，edge coverage 由 ELFUZZ 使用 [9]，instruction coverage 由 LLM4FUZZ 使用 [8]，它们都是同一信号家族的不同切片。因此「仅 3 篇」部分是度量命名碎片化所致，而非真正的稀少。

主线三：覆盖率为何被系统性低估——成因诊断

其一，评估仪器偏好（技术难度/资源壁垒）。覆盖率是连续、需长期 campaign、以五个 run 平均（CovRL 的度量方式 [3]）才能稳定量化的指标，与 benchmark 追求短平快、离散 pass/fail 的取向冲突。FUEL 自述每轮迭代 24.09 秒延迟、总成本约 $40.89 [4]，折射出「全覆盖-反馈闭环」的高资源门槛。

其二，认知盲区。覆盖率「长链路兑现」的因果链（覆盖↑→路径暴露↑→bug↑）在多轮 LLM 迭代的评测框架中被截断，社区更愿意直接以「修复率/漏洞率」等终局指标报告，把覆盖率降格为过程指标。

其三，反向证据强化低估论证。语义混合 fuzzing 论文 [10] 明确指出「多数 LLM 辅助 fuzzer 过度依赖 code coverage 作为唯一反馈，忽视高层语义多样性」，并提出语义新颖度反馈加以扩展 [10]；SAFuzz [11] 进一步以自适应策略证明纯覆盖率不足 [11]。这类「覆盖率不够」的批评与「覆盖率被低估」并不矛盾——它说明覆盖率是必要但非充分的基础信号，其作为基线驱动的价值被低估（被轻视），而非被高估。

分歧点与证据冲突

最大分歧在归因：程序执行反馈的高篇目支持度，究竟真实反映其效果优于覆盖率，还是反映「易测量性偏差」（crash/test 是天然离散、易报告，覆盖率需专门 instrument）。这一冲突由 CovRL 与 FUEL 的结果侧面激化——两者都以覆盖率驱动却取得了与执行反馈类工作相当甚至更优的 bug 发现成果 [3][4]，暗示覆盖率的效果可能被篇目统计所掩盖。另一冲突点是「覆盖率是否充分」：语义混合 fuzzing [10] 与 SAFuzz [11] 主张纯覆盖率不足，需要扩充语义信号，而 CovRL [3] 则证明覆盖率作为核心驱动已经很强。这一冲突的实质是「必要但非充分」——覆盖率是基础底座，但不排除需要叠加其他信号。

分析局限性

第一，核心证据缺口：不存在任何在统一 benchmark 上对「程序执行反馈 vs 覆盖率反馈」做 head-to-head 消融的研究，导致无法直接量化两类信号各自的可测改进贡献差。第二，覆盖率信号「仅 3 篇」的统计受度量命名碎片化（code/branch/edge/instruction coverage 分立）影响，叠加 KG 收录完整性问题（[10][11] 等扩展论文未被计入 code coverage 边），「3 篇」应视为下界而非精确值。第三，多数量化结论（53% 修复率 [1]、48 bug/11 CVE [3]、42 内存 bug [6]）来自不同语言、不同目标（Python 安全生成 vs JS 引擎 vs Rust crate），跨任务可比性弱，不宜直接横向比较绝对值。第四，上游 A1.1-a 矩阵报告与 A1.4-c 风险报告在当前环境不可访问，密度统计与危害评级均基于 KG 边重建并标记为独立估计，未能链接到 A1.4-c 的风险等级做跨 skill 一致性校验。第五，归因性结论（易测量性偏差、系统性低估机制）属中等置信推断，缺乏直接的元评估研究支撑。

结论

对本 RQ2.2 给出一致判定：「部分回答」。程序运行反馈（崩溃复现、测试执行、sanitizer 信号）贡献可测改进的直接证据较强，其有效性被 AutoSafeCoder [1]、VRpilot [2]、PAGENT [5]、deepSURF [6] 等多篇工作从不同角度反复验证。覆盖率作为自改进驱动的证据强度同样不低——CovRL [3] 发现 48 个真实 bug、11 个 CVE，FUEL [4] 以覆盖率驱动多种反馈，均证明覆盖率的强驱动力。

关于「覆盖率是否被系统性低估」：判断成立。其支持度靠后（code coverage 仅 3 篇）主要由三个机制造成——评估体系偏好离散终局指标、覆盖率需长 campaign 且度量命名碎片化、其跨语言跨域验证稀缺。覆盖率的价值是「必要但非充分」的基础底座，被低估而非被高估。未来的关键研究机会在于：建立统一 benchmark 对程序执行反馈与覆盖率反馈做受控消融，并量化覆盖率在 LLM 多轮自改进中的因果兑现链路。
