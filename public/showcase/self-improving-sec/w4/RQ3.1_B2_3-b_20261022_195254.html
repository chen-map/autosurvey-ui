摘要

本报告对 RQ3.1（评估基准分布偏斜有多严重、如何限制自改进结论的外推半径）进行了系统性数据集谱系审查。结论：分布偏斜在知识图谱中被系统性证实，且比提问中的计数（HumanEval 6 / SecurityEval 5 对 Vul4j / PatchEval / SEC-Bench 各 3）所暗示的更严重——实质是一种「语言—粒度—任务三重锁定」。安全代码生成侧被函数级、单语（Python）、合成 CWE 提示的 SecurityEval 一系基准锁定 [1][2][3]；仓库级、多语言数据集（Vul4j / PatchEval / SEC-Bench）仅服务于极少数「漏洞修复（AVR）」谱系的自我改进论文 [4][5][6]，与生成侧几乎不共享。

由此，自改进在「函数级 Python 安全生成」上的增益不能自动外推到「仓库级、跨语言、真实部署」场景。生成侧结论还叠加了标签噪声：静态分析器（CodeQL/Semgrep）与人工标注每样本一致率仅约 61–65% [2]。此外一支自我改进智能体工作（SEVERA）干脆绕开 CWE/安全代码，改在形式验证与客服任务上评估，暴露基准高度碎片化 [7]。

数据来源与规模

本分析基于知识图谱（KG）的结构化节点与边，共使用 20 轮工具调用、覆盖全部六类节点：dataset（235 个数据集/基准节点）、paper（141 篇论文）、problem（402 个问题节点）、method（385 个方法节点）、metric（256 个指标节点）、limitation（226 个局限节点）、assumption（100 个假设节点）。核心证据来自 evaluated_on 边（数据集使用）、problem 节点（基准偏斜/窄覆盖）、limitation 节点（Python-only、静态扫描器依赖、单项目范围）及边 evidence 字段中的直接引文。审计的数据集包括：SecurityEval、HumanEval、LLMSecEval、CyberSecEval、SecCodePLT、Vul4j、PatchEval、SEC-Bench、Multi-SWE-bench、Defects4J、SWE-bench、ExtractFix、VjBench、VulRepair dataset、DafnyBench 等。

主线一：生成侧被 SecurityEval 锁定为事实标准

KG 显示 SecurityEval（约 121–130 条提示、69–75 个 CWE，[datasetbenchmark_datasetbenchmark_securityeval_3915d1eec9]）是证据矩阵的核心枢纽。0064 在 LLMSecEval+SecurityEval 上测试提示工程对 LLM 模型安全性的影响 [1]；0226 用 SecurityEval+SecCodePLT+CyberSecEval 研究自生成漏洞提示与反馈修复 [2]；0309 报告 SecurityEval 上平均 76.2% 生成代码不安全，并在 Limitation 中明写「评估限于 Python，结论可能不外推」[3]；0315 在 SecurityEval 上报告相对 LLM 降低 13% 漏洞、静态分析器在 4 轮内修复 53% 漏洞 [3]。同时 HumanEval 仅用于功能正确性（pass@k），不构成安全评估依据 [3]。SecurityEval 的血缘是「由 CWE 场景派生的提示集」，本质是合成、面向单函数的提示，这把生成侧牢固锁定在函数粒度与单语 Python。

主线二：仓库级/多语言基准仅服务修复谱系的少数自进化论文

Vul4j（79 Java CVE）、PatchEval（1000 条 Go/Python/JS，常只用 230 条 Docker 子集，EviRepair 具体用到 Go 83/Python 70/JS 77）、SEC-Bench（200 C CVE + 100 OSS-Fuzz）确实被 EvoRepair [4]、MemRepair [5]、EviRepair [6] 使用，但这些都属于「修复（AVR）」谱系，与生成侧基准几乎不共享。RQ3.1 的「多语言/仓库级各仅 3」正说明它们只服务修复侧极少数的自进化工作——EvoRepair 的「经验自进化」、MemRepair 的「分层记忆」、EviRepair 的「证据驱动多智能体」——其结论无法覆盖生成侧自改进方法。0204 的 VRpilot 虽跨 C+Java（ExtractFix、VjBench、Vul4j），但以单文件局部化为前提 [8]。

主线三：基准偏斜与窄覆盖在 KG 中显式编码，部分作者自承

0241 把「Defects4J/SWE-bench 从维护良好的开源项目抽取、可能高估 legacy 系统性能」列为一等问题节点 problem_benchmark_bias_toward_modern_repositories，并指出不存在专为 legacy 代码（稀疏测试、缺文档）设计的基准 problem_lack_of_legacy_specific_benchmarks [9]。0153 承载 problem_narrow_benchmark_coverage（「基准集中于 Python 生成与 C/C++ 检测，CWE 分布分歧」）[2]。更关键的是，修复侧作者自己也承认局限：0589 明写「评估仅覆盖 PatchEval 与 SEC-bench，可能无法反映漏洞、语言、仓库、部署环境的全部多样性」[6]；0217 承认仅用 5 个 SWE-bench Python 仓库 [10]。这些不是推断，而是 KG 中带 0.85–0.95 置信度的显式节点与边。

分析局限性

本分析存在若干证据缺口与不确定性。其一，RAG 原文检索工具（search_paper_sections）在本环境不可用（调用返回 Unknown tool），故所有引用均来自 KG 结构化字段与边 evidence 字段的直接引文，无法逐段核对原文章节标题与相似度分值。其二，KG 的 evaluated_on 边同时包含 Paper 与 Method 头节点，使「使用篇数」的精确计数存在噪声，本报告以边 evidence 中明确的论文归属为准做保守计数。其三，PatchEval / SEC-Bench / Vul4j 的样本正负比与创建年份在 KG 描述中未披露，只能标注 provenance 部分未知，因此「极端正负不平衡对精度/召回扭曲」的量化结论无法完成，相关判断置信度受限。其四，0471（SEVERA）的形式验证/客服任务基准虽补充了基准碎片化的证据，但其与安全代码生成的关联属于间接推断。

结论

RQ3.1 的分布偏斜已被 KG 数据系统性证实，并呈现为比单纯计数更深刻的「语言—粒度—任务三重锁定」。函数级、单语 Python 的合成 CWE 基准（以 SecurityEval 为核心 [1][2][3]）主导生成侧评估；仓库级多语言基准（Vul4j / PatchEval / SEC-Bench）仅被极少数修复谱系自进化论文使用 [4][5][6]，与生成侧几无交集；标签来自静态分析器，与人工标注仅约 61–65% 一致 [2]。这使自改进在「函数级 Python 安全生成」上的增益（如降低 13% 漏洞 [3]）无法外推到仓库级、跨语言、真实部署场景，外推半径被显著收窄。修复侧自进化工作虽在仓库级基准上给出了跨语言信号，但其作者亦自承基准多样性不足 [6]。因此，领域评估结论的可信度在跨粒度与跨语言方向上应至少标记为 moderate 降级，亟需建立 legacy 专用、多语言、正负比透明的基准体系。
