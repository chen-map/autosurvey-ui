摘要

本报告回答 RQ4.2：功能保持（Functionality Preservation）在知识图谱中仅以一条孤立的 AssumptionConstraint 节点形式存在、未上升为 Metric 节点，这对"补丁类自改进"结论构成何种效度威胁，以及现有工作用什么替代手段测量功能保持、覆盖率如何。

核心发现是结构性的：功能保持概念（assumptionconstraint_functionality_preservation_0e2027b22b）已具备准形式化的伪公式定义——"对测试集 T 中所有 t，若 P(t)=Pass 则 P'(t)=Pass"——但三向反向图查询（requires / relaxes / targets）与 measured_by 均返回空，且全部 256 个 Metric 节点中没有任何一个以功能保持、回归或行为等价命名。这意味着整个 KG 把"补丁不得破坏既有功能"当作一个默认成立的前提而非可测量、可证伪的指标。现有工作实际用三类代理测量它：测试套件通过/plausible patch [1][2]、编译通过率 [2]、以及完全绕过行为保持的精确匹配 EM 与修复率 [3][2]。多篇论文从不同角度证伪了"测试通过 = 功能保持"的外推 [4][5][6]，人工评审虽为兜底却不可规模化 [7]，LLM 评审准确率仅 68%–79% 尚不足以替代 [8]。本 RQ 判定为 partial：威胁链条清晰，但替代手段覆盖率缺乏量化证据。

核心事实：功能保持是孤立约束而非度量

功能保持在本 KG 中是一个"有定义、无测量"的节点。它拥有一个接近数学形式的描述（∀t∈T, P(t)=Pass ⇒ P'(t)=Pass），但其节点在图谱中完全孤立：没有任何 Method 通过 requires 或 relaxes 边引用它，没有任何 Problem 通过 targets 边指向它，也没有任何 measured_by 边把它与某个 Metric 关联。与此同时，对全部 Metric 节点做名称过滤，唯一含"fun"子串的度量是 Functional correctness rate（metric_functional_correctness_rate_21f75744cb），它本身也仅由单篇论文 [1]（SecureVibeBench）关联，并非专门度量回归。这一结构事实直接回答了 RQ 的第一个问题：功能保持从未被上升为可测量、可报告的指标，它只是一个被默认成立的前提。

替代手段一：测试套件通过代理及其覆盖缺口

KG 中承担功能保持测量职责的主流手段是"测试套件通过"：plausible patch 被明确定义为"compiles and pass the test suite"[2][11]，Pass@1 定义为"pass all tests (functional and security)"[4]。这正是功能保持伪公式的直接操作化——但它们只验证被选中的行为，无法覆盖回归风险的主战场。[4] 的 problem_incomplete_feedback_for_patch_quality 给出了本 RQ 最关键的直接反驳："A passing test checks only selected behavior and functional success need not establish patch quality or security"。其配套限制进一步指出：Tests、compilers、reviewers 只直接评估产物（artifact），而仅间接监督被保留的更新（retained update），且"一个有效补丁可能产出过度泛化的记忆、不必要的技能或伤害后续任务的规则"。这构成对功能保持假设边界的逻辑证伪：覆盖率缺陷使"P(t)=Pass ⇒ P'(t)=Pass"无法外推到真实功能保持。

从测试侧看，[6] 记录了项目自带 test suite 判别力的不足——测试套件仅检测到少数攻击、防御常常静默失效，最佳过滤器仅拦截 47% 的对抗 issue。这说明即便项目已有测试，其作为功能/安全守门的有效性也显著不足。编译类指标（Compilable patches [2]）则更弱，只验证"能编译"，对行为保持几乎没有约束力。

上图为基于节点描述与关系边的定性评级，非原文报告的量化覆盖率。评级依据：测试套件类只覆盖被选中行为故为中等；EM 完全绕过行为保持故为 0；人工评审覆盖最完整但不可扩展。KG 中不存在名为"回归测试"或"行为等价"的独立 Metric 节点，因此无法给出精确覆盖率百分比——这一量化缺口是本 RQ 判为 partial 的直接原因。

替代手段二：EM 与修复率完全绕过功能保持

第二类替代手段不仅覆盖不足，而是完全绕过了功能保持。EM（Exact Match）衡量生成补丁与 ground-truth 补丁的表面一致性 [3][2]，它既不能确认语义等价，也无法识别行为回归：一个语义正确但语法不同的补丁会在 EM 下被判失败，反之一个通过测试但过度泛化的补丁可能在只报告修复率时被判成功。Repair success rate 类指标 [12][13] 同样只报告"修复了多少"，不报告"修复是否引入回归"。因此，凡以 EM 或 repair success rate 作为主要结论依据的补丁类自改进论文，其"改进"结论在功能保持维度上是未经检验的。

替代手段三：人工评审与 LLM 评审的兜底及其不可扩展性

在缺乏自动化功能保持度量的情况下，人工评审成为唯一相对可信的兜底，但代价是不可规模化。[7] RuleForge 的多阶段验证流水线明确"balancing automated testing with human expertise to minimize false positives while maintaining high detection rates"，但其 human review bottleneck 限制承认"处理量被人为限制以防止压垮执行最终验证的人类评审员"——即人工功能/质量评审构成吞吐瓶颈，覆盖率随规模骤降。（注：[7] 生成的是检测规则而非代码补丁，其"功能保持"体现为对良性流量低误报，FP 下降 67%、无 IP 匹配规则下降 71%、AUROC 0.75，并非代码回归保持，与补丁类自改进存在任务类型错位。）

用 LLM 替代人工评审亦不充分：[8] 的 LLM 验证准确率仅 68%–79%，被明确认为"不足以盲目信任"而仍需人工复核。此外 [5] FAULTLINE 从定义侧精确点出效度威胁：理想 PoV 测试须"有漏洞时失败、修复后通过"，而"确保修复后通过本身就是一个效度威胁"——这直接命中功能保持公式右侧条件 P'(t)=Pass。

分析局限性

本研究存在四点不确定性。其一，两篇冻结的证据矩阵论文与"补丁类自改进"存在任务类型错位：[7] RuleForge 生成检测规则、[10] MazeRunner 是渗透测试编排框架，均不对代码打补丁，无法为功能保持度量提供正面实例，其"功能保持"含义须分别理解为低误报（规则）与隐式运维约束（渗透测试）。其二，功能保持定义版本唯一且无冲突，缺乏多版本对照，推演效力只能定为定性逻辑——KG 中的"形式化"仅是描述性伪公式，未被任何方法作为可执行 oracle 使用。其三，RAG 原文检索工具本次不可用，无法核验部分论文更细的验证细节与精确覆盖率数字。其四，行为等价/回归测试在 KG 中没有独立 Metric 节点，故"替代手段覆盖率如何"只能作结构性回答（覆盖取决于测试集 T 的完备性），无法从结构化数据给出量化百分比。

结论

功能保持在本 KG 中仅以孤立 AssumptionConstraint 节点存在、未被上升为 Metric，这对"补丁类自改进"结论构成一个系统性的结构性效度威胁：所有以"补丁通过测试"为成功判据的自改进论文，其"改进"结论都建立在一个未被任何工作实际量化验证的假设之上。现有工作以三类代理替代测量：测试套件通过/plausible patch（覆盖取决于 T 完备性，只验证被选中行为）[2][4][11]、编译通过率（几乎无行为约束力）[2]、以及完全绕过行为保持的 EM 与修复率 [3][12][13]。多篇论文从测试覆盖、产物与更新之别、PoV 测试效度等角度证伪了"测试通过=功能保持"的外推 [4][5][6]，人工评审虽为兜底却因吞吐瓶颈而不可扩展 [7]，LLM 评审准确率 68%–79% 亦不足以替代 [8]。因此，覆盖率问题在结构化数据层面无法量化回答——这既反映了证据缺口，也恰恰印证了 RQ 的核心判断：功能保持的度量在主流工作中处于缺失状态。本 RQ 判定为 partial。
