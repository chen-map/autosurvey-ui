摘要

本报告针对子问题 RQ3.3（自改进方法在跨语言迁移、跨 CWE 族泛化、真实仓库规模部署上的分布外/OOD 证据）对知识图谱（KG）进行了系统性挖掘。核心结论：在 141 篇论文中，明确报告上述三类 OOD 证据的仅约 7–9 篇，且集中在自动化漏洞修复（AVR）方向；这些证据几乎全部以「补充实验」而非「主实验」形式出现，无一篇给出系统性的 OOD 敏感度曲线或失效临界点。跨 head benchmark 之外的分布外表现，在 KG 中大多只能得到定性描述或单点数值。

跨语言方面，仅 RAVEN [1]、EvoRepair [2]、MemRepair [3] 三篇真正做了跨语言/多语言测试；跨 CWE 方面，仅 RAVEN 以「未见漏洞类型泛化」为设计目标，而 Multi-LLMSecCodeEval [4] 与 SecCodePLT [5] 则从反面揭示了「残余 CWE 困难」与「评测工具覆盖度即隐性 CWE 边界」；仓库规模方面，MemRepair [3] 与 VulnResolver [6] 以 SEC-bench 提供了稀缺的真实仓库级证据，但 0438 [7] 与 Legacy APR 综述 [8] 均自认存在「竞赛短程序」「现代仓库」等分布偏置。综合判定：本子问题的答案状态为 partial——证据存在但稀疏，真实 OOD 部署的定量边界仍是领域空白。

数据来源与规模

分析基于知识图谱（KG）的结构化数据，共执行约 40 次工具调用，覆盖全部六类节点：

- 节点类型查询：problem（402 个）、method（385 个）、dataset（235 个）、metric（256 个）、limitation（226 个）、assumption（100 个）、paper（141 篇）；

- 关系挖掘：通过 get_relation / get_head_entity / get_tail_entity 检索 proposes、addresses、evaluated_on、measured_by、has_limitation、extends、compares_with、targets 等边，重点追踪每条边的 evidence 字段作为原文证据；

- 定向深读：系统扫描与 RQ3.3 主题相关的约 23 篇关键论文的关系子图（见 references），并对其 evaluated_on 与 has_limitation 边做逐一核对。

需说明：本执行环境中 search_paper_sections 工具不可用（返回 Unknown tool），因此原定的语义段落检索改由 KG 节点的 description 与关系边 evidence 字段替代，证据粒度较原文段落为粗。KG 中全部 assumption 节点的 requires/relaxes 边均为空，此为约束敏感度分析的关键结构限制。

结构限制提示：KG 中 100 个 assumption 节点全部为「无连边」的记录性条目（requires/relaxes 查询均返回空）。因此本报告无法从约束依赖关系构建「高敏感约束 → 方法 → 证据论文」的链式剖面，凡涉及拐点数值的字段一律标注 sensitivity_data: absent，未以其他论文数据推定。

二、跨语言迁移证据：存在但极薄

真正做了跨语言测试的仅三篇。RAVEN [1] 明确以 Vul4j（Java，随机 23 个 CVE 子集）作为「out-of-distribution」泛化检验，并声称其 agentic RAG 设计旨在摆脱「单语言评估」这一既有缺陷（其问题节点 problem_single_language_evaluation 直接指出「既有评估常局限于单一编程语言」）。EvoRepair [2] 在 SEC-bench（C，200 实例/29 项目）、PatchEval（JS/Python/Go，230 实例子集）、Vul4j（Java，79 CVE，且自称与前者「语言与 CVE 构成正交」）三套数据上验证经验迁移，是现有最强的跨语言迁移证据。MemRepair [3] 在 SEC-bench（C/C++）与 PatchEval（Go/Python/JS）双栈评估。

相反，大量证据矩阵内工作是单语种：SecureFixAgent [13] 仅 Python，End-to-End Secure Code [10] 仅 Python（其 limitation_python_only_scope 明确承认「结论可能无法泛化到其他语言」），而 GRASP [14] 也仅 Python。需特别指出，矩阵指定优先查询的 AegisLLM [15] 完全不在代码-CWE 轴上——其评估基准为 WMDP、MMLU、MT-Bench、TOFU、StrongREJECT，聚焦 LLM 越狱与信息泄露防御，与本 RQ 的语言/CWE 轴正交，这是证据矩阵与子问题之间的一处映射错配。

三、跨 CWE 族泛化：以「残余困难」而非「有效区间」形式出现

真正触及「未见漏洞类型」的只有 RAVEN [1]，其问题节点明确指出「既有 AVR 框架大多局限于内存相关、可局部修复的漏洞，对未见漏洞类型的泛化未被充分探索」。反面证据更为有力：Multi-LLMSecCodeEval [4] 的局限性直接写明「即便使用多模型集成，某些 CWE 依然具有挑战」，并同时指出 LLM「无法从合成基准泛化到真实世界项目」；SecuCoGen [11] 仅覆盖 21 个漏洞类型且自认样本仅 180 条，单语言泛化未被探索；SecCodePLT [5] 名义覆盖 27 类 CWE，却因 CodeQL 不支持而直接剔除 6 类，实际仅评估 21 类/1,071 样本——这一剔除本身即说明「评测工具的覆盖度构成跨 CWE 评估的隐性边界」。此外，Persistent Human Feedback [12] 以「窄基准覆盖」问题为立论基础，指出代码生成集中于 Python、漏洞检测集中于 C/C++，且两域 CWE 分布彼此分歧。

四、真实仓库规模部署：稀缺证据与自认偏置

MemRepair [3]、VulnResolver [6]、RAVEN [1] 都以 SEC-bench（200 issue / 29 个 C 项目、仓库级端到端）为设置，是当前较稀缺的真实仓库规模代表；其中 MemRepair 还额外使用 Multi-SWE-bench 的 C++ 子集。VulnResolver 更进一步，用 SEC-bench-lite（80 issue）评估有效性、用 SEC-bench-full（200 issue）评估泛化（RQ3），是少数显式区分「有效性」与「泛化」的工作。

然而，规模证据的可迁移性被多处自认偏置削弱：0438 [7] 明确承认其评估仅限于「竞赛风格的短 C/C++ 程序（3,242 个）」，可能「高估大型工业代码库上的表现」，且其分析通道仅编译、CodeQL、KLEE 三条，覆盖本就不完全；Legacy APR 综述 [8] 则直指 Defects4J/SWE-bench 均取自「活跃维护、文档完善」的项目，其修复成功率「无法迁移到遗留环境」，且「尚不存在针对遗留代码难点（稀疏测试、缺文档、旧工具链）的专用基准」。此外，「规模」这一变量在各论文中口径不一（issue 数 vs 项目数 vs 程序长度），导致跨论文的边界对比无法直接对齐。

五、跨方法边界对比与失效风险

在语言维度上，EvoRepair [2] 的有效跨度最宽（C + JS/Python/Go + Java 三栈，且含正交语言验证），SecureFixAgent [13] 与 End-to-End Secure Code [10] 最窄（仅 Python）；边界突破者均为「增加语言覆盖 + 检索/经验迁移」这一类设计，包括 EvoRepair、MemRepair [3]、RAVEN [1]。在 CWE 维度上，SecCodePLT [5] 名义覆盖最广（27 类）但实际仅 21 类可评测，RAVEN 是唯一以未见类型泛化为设计目标的突破者。在仓库规模维度上，MemRepair [3] 与 VulnResolver [6] 覆盖最宽（SEC-bench 级），0438 [7] 最窄（竞赛短程序）。

必须强调：三类变量上的失效临界点（拐点）无一被报告。各论文的语言/CWE/规模定义虽大体一致（按语言种类、CWE 类数、issue/项目数），但性能-变量曲线的具体拐点数值均缺失，跨方法比较只能停留在「覆盖范围」层面，无法给出「何时应切换方法」的定量阈值。此外，RAVEN 将「同任务换语言」标注为 OOD，与真正的训练/部署分布迁移在强度上无法等同，这一口径差异在横比时需谨慎。

七、约束盲区与未测试的高敏感约束

KG 中全部 assumption 节点无连边，这一结构缺口本身即揭示了三个领域级约束盲区：

1. 「Python-only evaluation」——该高影响约束无任何方法报告跨语言的消融/敏感度曲线，一旦迁移到 C/Java/JS，有效性是否保持尚无量化证据（仅 RAVEN/EvoRepair 提供定性或单点迁移，无失效阈值）。

2. 「CWE identifier provided by upstream tools」——多数方法默认上游工具已正确给出 CWE 标签，但无实验测试「CWE 标签错误/缺失」时的性能衰减；而 VulnResolver [6] 明确指出依赖手工 CWE 标注本身就是方法痛点，此约束一旦违反将系统性削弱整类方法。

3. 「基准内→基准外代理假设」（隐性）——「基准内性能可代表真实仓库性能」是全部证据矩阵论文的隐含前提，但 0153 [12]、0309 [10]、0470 [4]、0241 [8] 从不同角度均指出该前提被违反（静态分析代理不可靠、合成→真实不泛化、现代仓库偏置）。这是领域最需要消融研究、却几乎没有系统性 OOD 敏感度报告的盲区。

分析局限性

（1）**工具限制**：本环境 search_paper_sections 语义检索工具不可用（返回 Unknown tool），原定的原文段落精读改由 KG 节点 description 与关系边 evidence 字段替代，证据粒度为摘要级而非段落级，score 值来自 KG 边置信度而非语义相似度，精度略低。

（2）**KG 结构缺口**：全部 100 个 assumption 节点无 requires/relaxes 边，无法构建含拐点的「约束敏感度剖面」，相关字段一律标注 sensitivity_data: absent，未以其他论文数据反推。这是本次分析最关键的置信度限制。

（3）**覆盖范围**：141 篇中仅系统扫描与 RQ3.3 直接相关的约 23 篇，未做穷尽枚举；对方法-数据集对的枚举可能遗漏边缘证据。

（4）**口径不一致**：「规模」在 KG 中缺乏统一定义（issue 数 vs 项目数 vs 程序长度），跨论文边界对比不可直接成立；「CWE 覆盖」存在「名义覆盖」与「实际可评测覆盖」两种口径，横比需谨慎。

（5）**矩阵错配**：证据矩阵指定的 AegisLLM [15] 并不贡献本 RQ 证据，说明证据矩阵与该子问题的映射本身存在覆盖偏差，提示下游应复核矩阵选文。

综合置信度约 0.78：OOD 证据「存在性」判断为高置信（有明确边证据支撑），但「定量边界与拐点」判断为低置信（原文与 KG 均缺失），已如实标注 absent 而非估算填补。

结论

RQ3.3 的答案是 partial 而非 answered：**跨语言迁移、跨 CWE 族泛化、真实仓库规模部署三类分布外证据确实存在，但稀疏（约 7–9 篇）、以补充实验或定性描述的形式存在，且几乎没有任何一篇报告失效临界点。** 最强的跨语言证据来自 EvoRepair [2]（C + JS/Python/Go + Java 三栈、正交语言/CVE 验证）与 RAVEN [1]（明确的 Vul4j OOD 检验），最稀缺的仓库规模证据来自 MemRepair [3] 与 VulnResolver [6]（SEC-bench 级），跨 CWE 泛化则几乎由 RAVEN 单篇承担设计目标、并由 Multi-LLMSecCodeEval [4] 与 SecCodePLT [5] 的反面证据（残余 CWE 困难、CodeQL 剔除 6 类）加以约束。

更重要的元结论是：该领域当前面临的核心盲区不是「某个方法不够鲁棒」，而是「约束本身从未被系统性测试」——Python-only、上游 CWE 标注可用、基准内→基准外代理这三个前提，均无对应的消融/敏感度研究，构成本领域最需要补课的地方。下一阶段的证据缺口明确指向：跨语言的性能-变量曲线、未见 CWE 族的失效阈值、以及遗留代码/大规模工业代码库的专用基准。
