# Skill: B2.6-b 科研成果可复现性诊断

**层级**：S2.6 资源、可复现性与反馈核算层 · [V3 新增]  
**RQ类型**：花多少钱？能复现吗？（开源完备性 / 工程文化）  
**元认知逻辑**：系统审查领域内论文的可复现性状态，从代码公开性、依赖明确性、数据可访问性、随机性控制四个维度构建「可复现性画像」，量化领域的开放科学文化成熟度。  
**认知基准面**：可复现性不只是「有没有代码」——如果方法的依赖组件在 KG 中没有节点（未知依赖），或方法依赖的 `requires` 边指向未公开的资源，可复现性在结构上就已经是 compromised 的。

---

## Goal

对 Solution Space 中的所有方法，执行结构化可复现性审查，识别复现障碍的类型与分布规律，量化领域整体可复现性水平，为科研可信度评估提供客观依据。

---

## Inputs

- `knowledge_graph/nodes/methods.json` — KG 方法节点，含 `code_url` 属性（若有）
- `paper_cards/parsed/` — Paper Cards，提取 Implementation / Data Availability / Reproducibility 章节
- `knowledge_graph/nodes/papers.json` — 论文元数据（year、venue、authors字段）

---

## Execution Steps

### Step 1: 代码可用性审查（文本搜索驱动）

**为什么这样做**：代码可用性信息散布在多个位置（Data Availability 章节、Footnote、Abstract 的最后一段、Repository 链接）。必须用关键词搜索系统性覆盖所有可能位置，而不仅检查固定章节。

```python
# 搜索代码公开声明
code_availability_snippets = search_paper_sections(
    paper_cards_root="paper_cards/parsed",
    query="code available at|implementation available|github.com|open source|source code|gitlab.com|zenodo",
    topk=20
)

# 搜索「申请可得」声明（upon_request）
upon_request_snippets = search_paper_sections(
    paper_cards_root="paper_cards/parsed",
    query="code available upon request|available upon reasonable request|contact author",
    topk=10
)
```

代码可用性分类：
- `available`：代码公开且可访问（GitHub/Zenodo 等），必须有明确 URL
- `upon_request`：论文明确声明「Code available upon reasonable request」
- `none`：无任何代码公开声明

**`upon_request` 状态必须来自论文明确声明，不得因缺少代码链接就推断为 `upon_request`。**

**不得通过搜索外部平台（如 GitHub）来获取代码可用性信息——只能依据论文文本。**

### Step 2: 依赖完备性审查（KG requires 边 + 文本）

**为什么这样做**：依赖不完备是隐性的可复现性障碍——代码有了，但运行代码所需的组件（特定版本的框架、专有数据集、外部 API）如果无法获取，代码等于不可用。KG 的 `requires` 边正是记录这类依赖关系的结构化来源。

```python
all_methods = get_entity_by_type(loader, "method")
for method in all_methods:
    method_id = method["id"]
    # 获取该方法的所有依赖（requires 边的 tail）
    required_components = get_tail_entity(loader, "requires", method_id)

    missing_dependencies = []
    for component in required_components:
        # 检查依赖的组件是否有对应的 KG 节点（有节点 = 已被社区记录，通常意味着可获取）
        # 若 requires 边指向一个没有进一步信息的节点，可能是未公开的专有资源
        component_evidence = get_evidence_papers(loader, component["id"])
        if not component_evidence:
            missing_dependencies.append(component)

    method["missing_kg_dependencies"] = [c["id"] for c in missing_dependencies]
    method["dependency_reproducibility_risk"] = len(missing_dependencies) > 0
```

同时检查论文文本中的依赖声明：
- 是否提供了完整的环境依赖说明（requirements.txt / Dockerfile / conda env）？
- 是否说明了特定版本的关键依赖（如 CUDA 版本、特定库版本）？

### Step 3: 数据集可访问性 + 随机性控制审查

**数据集可访问性**：

```python
# 搜索数据集可用性声明
dataset_snippets = search_paper_sections(
    paper_cards_root="paper_cards/parsed",
    query="dataset available|data available at|publicly available dataset|benchmark available",
    topk=15
)

# 检测是否使用私有/专有数据集
private_data_snippets = search_paper_sections(
    paper_cards_root="paper_cards/parsed",
    query="proprietary data|internal dataset|not publicly available|confidential",
    topk=10
)
```

**随机性控制**：

```python
# 搜索随机种子控制
seed_snippets = search_paper_sections(
    paper_cards_root="paper_cards/parsed",
    query="random seed|fixed seed|seed 42|reproducibility seed",
    paper_ids=[...],
    topk=15
)

# 搜索方差报告（统计但无种子也是部分可控）
variance_snippets = search_paper_sections(
    paper_cards_root="paper_cards/parsed",
    query="random seed|variance|standard deviation|error bar|confidence interval|mean ± std",
    paper_ids=[...],
    topk=15
)
```

**随机种子控制的评估只基于论文文本描述，不得通过查看代码来确认。**

### Step 4: 计算可复现性评分（五维度量化）

**为什么这样做**：原始四维度框架（代码/依赖/数据/随机性）已可涵盖核心可复现性因素。将 KG 依赖完备性作为第五个维度加入，使评分更能反映结构性可复现性障碍。

对每篇论文，基于五维度状态计算可复现性评分（0~5 分，每维度 1 分）：
- **代码可用**：available = 1 | upon_request = 0.5 | none = 0
- **依赖完备**：全部可获取 = 1 | 部分说明 = 0.5 | 无说明/有未知依赖 = 0
- **数据可访问**：public = 1 | restricted = 0.5 | inaccessible/proprietary = 0
- **随机种子固定**：有种子 = 1 | 有统计但无种子 = 0.5 | 无控制 = 0
- **KG 依赖完整性**：`requires` 边的所有依赖均有证据 = 1 | 部分缺失 = 0.5 | 有未知依赖 = 0

```
reproducibility_score = sum(dimension_scores)  # 0~5
```

评分 < 2.5 标注为 `Low Reproducibility`；评分 ≥ 4.0 标注为 `High Reproducibility`；其余为 `Partial Reproducibility`。

**若论文无 `Data Availability` 章节，强制标注所有维度为 `No Statement`，不得从其他章节推断。**

### Step 5: 识别工程文化趋势

结合论文发表年份，分析领域可复现性是否在改善（近期论文代码公开率是否提升）。

计算按年份分组的代码公开率，若近三年的公开率显著高于早期 → `trend: improving`；无显著变化 → `trend: stable`；近期下降 → `trend: declining`。

### Step 6: 原文溯源验证

对所有分析结论中引用的证据，使用 `search_paper_sections` 工具在 `paper_cards/parsed/` 中精确定位原文片段：

```python
snippets = search_paper_sections(
    paper_cards_root="paper_cards/parsed",
    query="<分析结论的关键词>",
    paper_ids=[<涉及的paper_id列表>],
    topk=3
)
```

每条关键结论必须附带：
- `paper_id`：来源论文ID（对应 `knowledge_graph/nodes/papers.json` 中的记录）
- `section`：原文章节标题
- `paragraph_snippet`：原文片段（≥20字，直接引用，禁止改写）
- `score`：语义相似度分值

**无法找到原文片段支撑的结论必须标注 `evidence: unverified`，不得作为最终结论输出。**

## Key Rules

- **可复现性判断只能来自论文的 Data Availability/Implementation 章节**，不得通过搜索外部平台（如 GitHub）来获取代码可用性信息。
- 若论文无 `Data Availability` 章节，强制标注所有维度为 `No Statement`，不得从其他章节推断。
- `upon_request` 状态必须来自论文明确声明（如「Code available upon reasonable request to the corresponding author」），不得因缺少代码链接就推断为 `upon_request`。
- 随机种子控制的评估只基于论文文本描述，不得通过查看代码来确认。
- 若某 venue 有明确的可复现性要求（如强制提交代码），需在报告中注明该 venue 政策，上下文化解读该 venue 论文的低可复现率。
- **KG `requires` 边依赖完整性检查是强制步骤**：必须对每个方法执行 `get_tail_entity(loader, "requires", method_id)`，检查依赖组件是否有 KG 证据；有未知依赖的方法在 `kg_dependency_integrity` 维度得 0 分。
- **代码可用性搜索必须使用 `search_paper_sections` 全文覆盖**（`topk=20`），不得仅检查 Data Availability 章节；代码链接可能出现在 Abstract、Footnote 或 Conclusion 中。
- **认知坐标纪律**：本技能的核心产出是「可复现性的结构性障碍」——KG 中的未知依赖比「没有写 Data Availability」更难修复；报告必须区分「文化障碍」（没有写出来）和「结构障碍」（依赖本就不可获取）。
