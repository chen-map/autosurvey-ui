# Skill: B2.3-a 评估实践元分析

**层级**：S2.3 验证度量层 · Evaluation Metrics & Benchmarks  
**RQ类型**：效果好不好？（评估方法论）  
**元认知逻辑**：不直接评价「方法效果」，而是将「如何评估」本身作为研究对象，统计领域内评估设计的形式分布、指标偏好、基线选择，揭示评估方法论的系统性规律与盲区。核心洞察不在于比较数字，而在于比较「测量框架」——哪些维度被系统性地度量，哪些维度被系统性地忽视。  
**认知基准面**：度量框架的缺失比方法性能的缺失更危险——一个性能差但被充分度量的方法，其局限性是已知的；一个性能看似好但度量框架有盲区的方法，其真实局限性是未知的，这是更大的风险。

---

## Goal

对 KG 中所有解法对应的评估设计进行全面编码与统计，揭示领域评估实践的分布规律，为评估体系可信度提供元层面的分析。重点不在统计数字，而在识别「哪些问题类型没有对应的度量维度」——这些是评估框架的结构性盲区。

---

## Inputs

- `knowledge_graph/nodes/methods.json` — KG 方法节点
- `knowledge_graph/nodes/dataset_nodes.json` — 数据集节点
- `paper_cards/parsed/` — Paper Cards，重点提取 Evaluation / Experiment 章节
- `knowledge_graph/nodes/papers.json` — 论文元数据（year、venue、authors字段）

---

## Execution Steps

### Step 1: 以 KG metric 节点为基础提取评估维度本体

**推理目标**：为什么从 KG metric 节点出发而不是从 Paper Cards 的 Evaluation 章节出发？因为 metric 节点是经过规范化的评估维度表示——`get_entity_by_type(loader, "metric")` 的返回结果是领域评估维度的完整枚举，而 Paper Cards 中的指标名称可能因表述不一致而难以合并统计。

**操作流程**：

```python
all_metrics = get_entity_by_type(loader, "metric")
# 每个 metric 节点有 canonical_name, description, label 字段
```

对每个 metric 节点，统计有多少方法以其作为评估指标：
```python
for metric in all_metrics:
    methods_using_metric = get_head_entity(loader, "measured_by", metric["node_id"])
    metric_usage_count = count(methods_using_metric)
    # 高使用频次 metric = 社区共识评估维度
    # 低使用频次 metric = 小众或新兴评估维度
```

将所有 metric 节点按 `canonical_name` 和 `description` 的语义相似度聚类，构建评估维度本体：
- 精度类（Precision/Recall/F1/Accuracy）
- 效率类（Latency/Throughput/Memory）
- 质量类（BLEU/CodeBLEU/Edit Distance）
- 鲁棒性类（Robustness/Generalization）
- 用户体验类（User Study/Satisfaction）

聚类时注意：若两个 metric 的 `canonical_name` 相似但 `description` 中的 K 值不同（如 Precision@3 vs Precision@10），必须标注定义不一致，不得视为同一指标合并统计。

### Step 2: 统计每个评估维度的社区覆盖率

**推理目标**：高使用频次的 metric 不只是「流行指标」，它代表社区对「什么值得被测量」的共识——这个共识本身是一种认识论立场，需要被审视，而不只是被记录。

**操作流程**：

计算每个 metric 类别的覆盖率（使用该类别 metric 的论文数 / 总论文数）：
- 覆盖率 > 70% = 社区共识维度（被广泛接受为评估必要项）
- 覆盖率 30%~70% = 可选维度（部分社区重视）
- 覆盖率 < 30% = 边缘维度（可能是新兴或被忽视）

对共识维度，验证其历史趋势：
```python
# 获取使用该 metric 的论文，按年份排序
metric_papers = get_head_entity(loader, "measured_by", metric_id)
paper_years = [get_paper_year(p["context_paper_id"]) for p in metric_papers]
# 若该 metric 主要出现在早期论文中 → 可能是遗留指标
# 若主要出现在近期论文中 → 新兴标准
```

利用 `context_paper_id` 的 `created_at` 时间戳识别评估时尚（evaluation fashion）：
- **新兴标准**：仅在近 2 年论文中出现的 metric
- **遗留指标**：仅在 2 年前论文中使用，近年消失的 metric

### Step 3: 检测评估盲区——问题类型与度量维度的对应缺口

**推理目标**：评估盲区的精确定义是「存在某类 problem 节点（方法所 addresses 的问题），但没有对应的 metric 节点被用来度量该 problem 的解决质量」。这是结构性盲区，不是随机的指标遗漏。

**操作流程**：

获取所有 problem 节点（通过 `addresses` 边从方法反推）：
```python
all_problems = set()
for method in all_methods:
    problems = get_tail_entity(loader, "addresses", method["node_id"])
    all_problems.update([p["node_id"] for p in problems])
```

对每个 problem 类型，检查解决该 problem 的方法是否有对应的 metric：
```python
for problem_id in all_problems:
    # 找出解决该 problem 的方法
    methods_for_problem = get_head_entity(loader, "addresses", problem_id)
    # 找出这些方法使用的所有 metric
    metrics_for_problem = union([
        get_tail_entity(loader, "measured_by", m["node_id"])
        for m in methods_for_problem
    ])
    
    if count(metrics_for_problem) == 0:
        # 该 problem 类型无任何度量维度 → 绝对盲区
        blind_spots.append({"problem_id": problem_id, "type": "absolute_blind_spot"})
    elif all(m["label"] == "efficiency" for m in metrics_for_problem):
        # 该 problem 只被效率指标度量，无质量指标 → 质量盲区
        blind_spots.append({"problem_id": problem_id, "type": "quality_dimension_missing"})
```

评估盲区类型分类：
- **效率盲区**：有精度 metric 但无效率/成本 metric
- **规模盲区**：在小数据集评估但无工业规模评估
- **鲁棒性盲区**：只报告平均性能，无最差情况/分布外场景
- **公平性盲区**：无跨子群体（如跨编程语言、跨项目）的分层评估

声明某维度被「系统性忽视」需至少 3 篇论文数据支撑。

### Step 4: 评估设计编码（覆盖所有论文）

对每篇论文的评估章节进行结构化编码：

**评估形式**（可多选）：
- `controlled_experiment`：有对照组的受控实验
- `ablation_study`：消融实验
- `case_study`：典型案例研究
- `user_study`：用户调研
- `theoretical_proof`：理论证明
- `simulation`：仿真实验

若某论文无 Evaluation 章节，标注 `evaluation_section: absent`，不得从其他章节推断评估设计。

**基线类型**：
- `no_baseline`：无基线
- `rule_based`：规则方法基线
- `prior_sota`：前期 SOTA 方法基线
- `ablation`：自身消融版本

### Step 5: 识别指标异质性——评估不可比性审计

**推理目标**：指标异质性不只是统计障碍，它揭示了「社区尚未就何为有效解决方案达成共识」——若不同论文用完全不同的指标，说明该领域对「什么叫解决了这个问题」还没有统一答案，这本身是一个重要的领域诊断。

**操作流程**：

计算不同论文间 metric 集合的 Jaccard 相似度：
- Jaccard ≈ 0（无共同 metric）= 评估完全不可比
- Jaccard > 0.5（超过一半指标共享）= 评估基本可比

按 problem 类型分组后分别计算 Jaccard，识别「哪些任务类型的评估已经收敛」和「哪些任务类型的评估仍然碎片化」。

### Step 6: 对抗性验证——共识度量的合法性审查

**推理目标**：高频使用的 metric 往往被视为「理所当然的标准」，但这种共识可能是历史路径依赖而非最优选择。对抗性验证要求审查：社区共识 metric 是否真正度量了问题的核心属性？

**操作流程**：
- 对每个覆盖率 > 70% 的共识 metric，从 KG 中查找其是否有 `has_limitation` 边：
```python
metric_limitations = get_tail_entity(loader, "has_limitation", metric_id)
```
- 若某共识 metric 有已知局限性（如「Precision/Recall 无法区分误报的严重程度」），在报告中标注这是一个「有缺陷的共识标准」，记录其局限性并引用相关论文
- 搜索对共识指标的批评性文献：
```python
metric_critique_snippets = search_paper_sections(
    paper_cards_root="paper_cards/parsed",
    query="metric is insufficient|does not capture|fails to measure|beyond accuracy|evaluation gap",
    paper_ids=all_paper_ids,
    topk=5
)
```

### Step 7: 原文溯源验证

对所有分析结论中引用的证据，使用 `search_paper_sections` 工具精确定位原文片段：

```python
snippets = search_paper_sections(
    paper_cards_root="paper_cards/parsed",
    query="<分析结论的关键词>",
    paper_ids=[<涉及的paper_id列表>],
    topk=3
)
```

每条关键结论必须附带：
- `paper_id`：来源论文ID
- `section`：原文章节标题
- `paragraph_snippet`：原文片段（≥20字，直接引用，禁止改写）
- `score`：语义相似度分值

**无法找到原文片段支撑的结论必须标注 `evidence: unverified`，不得作为最终结论输出。**

## Key Rules

- **metric 节点是评估维度的主要来源**，`get_entity_by_type(loader, "metric")` 必须在 Step 1 执行，不得仅从 Paper Cards 文本归纳指标。
- 编码必须来自 Paper Cards 的 Evaluation 章节，若某论文无 Evaluation 章节，标注 `evaluation_section: absent`，不得从论文其他部分推断评估设计。
- 评估形式编码可多选，不得强制单选。
- 「评估不可比性」结论需在最终汇报中突出，不得将不同指标的数字直接比较。
- 若某指标的定义在不同论文中存在细微差异（如 Precision@K 的 K 不同），必须标注定义不一致，不得将其视为同一指标汇总。
- 评估盲区的识别需至少 3 篇论文数据支撑才能声称某维度被「系统性忽视」。
- **有缺陷的共识指标审查是必选步骤**——覆盖率 > 70% 的 metric 必须检查其 `has_limitation` 边，不得无条件接受高频指标的合法性。
- **认知坐标规则**：每次执行在 Checkpoint Output 第一行记录认知坐标，格式为 `[认知坐标: S2.3 · 元评估空间构建 · <本次分析的评估维度本体和盲区类型>]`。
