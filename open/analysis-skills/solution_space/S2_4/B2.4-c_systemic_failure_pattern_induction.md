# Skill: B2.4-c 系统性缺陷归纳

**层级**：S2.4 效能对比层 · Comparative Efficacy & Trade-offs  
**RQ类型**：优劣势如何？（是否真优于SOTA）  
**元认知逻辑**：不分析单个方法的缺陷，而是横向归纳所有方法共同失败的场景，分析失败是否源于当前技术范式的共同假设缺陷，揭示该技术路线的系统性天花板（ceiling）。  
**认知基准面**：limitation 节点不是方法的「缺点备注」——它们是失败实例的枚举；被多个不同范式的方法共享的 limitation 节点，就是技术天花板的指纹。

---

## Goal

从 KG 的 `limitation` 节点出发，横向收集所有方法的失败场景，通过共享分析识别「跨方法的共性失败模式」，判断这些失败是范式层面的不可避免还是工程层面的可修复，确定技术路线的系统性天花板。

---

## Inputs

- `knowledge_graph/nodes/methods.json` — KG 方法节点
- `knowledge_graph/nodes/limitations.json` — KG limitation 节点（主要数据源）
- `knowledge_graph/nodes/assumptions.json` — KG assumption 节点（用于溯源范式缺陷）
- `paper_cards/parsed/` — Paper Cards，提取 Limitation / Failure Analysis / Discussion 章节
- `working_memory/rq_{id}/B2.4-b_sensitivity_report.json` — 敏感性分析结果（可选）
- `working_memory/rq_{id}/A1.5-b_bottleneck_report.json` — Problem Space 硬约束（可选）

---

## Execution Steps

### Step 1: 从 KG limitation 节点系统性枚举失败实例

**为什么这样做**：从 Paper Cards 文本中手工提取失败场景，依赖分析者的阅读覆盖度，容易遗漏。KG 的 `limitation` 节点是经过结构化抽取的失败实例库——这是系统性分析的正确起点。

```python
# 主数据源：KG limitation 节点
all_limitations = get_entity_by_type(loader, "limitation")

for limitation in all_limitations:
    limitation_id = limitation["id"]
    # 找到所有拥有该 limitation 的方法
    affected_methods = get_head_entity(loader, "has_limitation", limitation_id)
    limitation["affected_methods"] = [m["id"] for m in affected_methods]
    limitation["affected_count"] = len(affected_methods)

    # 获取支撑证据论文
    evidence_papers = get_evidence_papers(loader, limitation_id)
    limitation["evidence_papers"] = [p["id"] for p in evidence_papers]
```

同时，补充从 Paper Cards 的 Limitation / Failure Cases 章节提取的失败场景（作为 KG 节点的补充，填补 KG 可能未完整提取的内容）：
- 失败场景描述
- 失败触发条件（什么输入/参数导致失败）
- 失败模式类型（误报激增/漏报/输出幻觉/推理超时/内存溢出等）

### Step 2: 横向聚类共性失败模式（基于共享 limitation 节点）

**为什么这样做**：通过 KG 的结构，我们可以精确识别「被多个方法共享的同一个 limitation 节点」——这比文本语义聚类更可靠，因为它是明确的结构化关联而非近似匹配。

**聚类标准**：
- **强共性**：同一个 `limitation_id` 被 ≥ 3 个不同方法的 `has_limitation` 边指向
- **弱共性**：不同 `limitation_id` 但语义相近（通过文本相似度判断，需人工确认）

```python
# 识别高共享度 limitation（范式级失败的候选）
systemic_candidates = [lim for lim in all_limitations if lim["affected_count"] >= 3]

# 关键过滤：这些方法是否来自不同技术范式？
# 来自同一范式的多个方法共享 limitation ≠ 范式级缺陷（可能只是范式内部实现问题）
for candidate in systemic_candidates:
    # 获取 affected_methods 的范式归属（来自 B2.1-a 的范式分类）
    paradigms_affected = set()
    for method_id in candidate["affected_methods"]:
        paradigm = lookup_method_paradigm(method_id)  # 从 B2.1-a 结果中查找
        paradigms_affected.add(paradigm)
    candidate["cross_paradigm"] = len(paradigms_affected) >= 2
    candidate["affected_paradigms"] = list(paradigms_affected)
```

**「范式缺陷」初步候选**：`affected_count ≥ 3` 且 `cross_paradigm = True` 的 limitation 节点。

**失败模式必须来源于多篇文献交叉验证，不可将单一实现的 Bug 泛化为范式缺陷。**

### Step 3: 判断失败来源：范式缺陷 vs 工程缺陷（通过 assumption 链溯源）

**为什么这样做**：区分范式缺陷和工程缺陷的关键不是「是否多个方法都有这个问题」，而是「这个失败能否追溯到一个所有这些方法共同 requires 的 assumption 节点」。若能，则该 assumption 就是范式的硬性前提，失败是范式级的。

```python
for pattern in systemic_candidates:
    if not pattern["cross_paradigm"]:
        pattern["failure_source"] = "implementation_level"
        continue

    # 检查失败是否可追溯到共同的 assumption
    shared_assumptions = []
    for method_id in pattern["affected_methods"]:
        method_assumptions = get_tail_entity(loader, "requires", method_id)
        if not shared_assumptions:
            shared_assumptions = [a["id"] for a in method_assumptions]
        else:
            # 取交集：所有受影响方法都 requires 的 assumption
            current_ids = [a["id"] for a in method_assumptions]
            shared_assumptions = [a for a in shared_assumptions if a in current_ids]

    if shared_assumptions:
        # 存在共同的 assumption → 范式级缺陷
        pattern["failure_source"] = "paradigm_level"
        pattern["paradigm_assumption_violated"] = shared_assumptions
    else:
        # 无共同 assumption → 实现层面的收敛失败（多个独立实现碰巧都有问题）
        pattern["failure_source"] = "mixed"
```

对每个「范式缺陷」候选，验证其核心假设：
- **范式缺陷**（Paradigm-level）：该失败来自当前技术路线的核心假设，不同实现都无法避免。判断标准：能否通过工程改进（更多数据、更大模型、更好算法）克服？若不能，则为范式缺陷。
- **工程缺陷**（Implementation-level）：该失败来自特定实现的局限，原则上可修复。判断标准：是否有某个方法已经部分解决了该失败模式？

### Step 4: 识别技术路线天花板（通过 relaxes 边的缺失判断）

**为什么这样做**：天花板的客观判据不是「感觉已经到极限了」，而是：对于某个范式级失败所违反的 assumption，KG 中是否存在任何方法有 `relaxes` 边指向它？如果没有，说明没有任何已知工作成功松弛了该约束——这就是当前技术天花板的客观证据。

```python
for paradigm_failure in paradigm_level_failures:
    for assumption_id in paradigm_failure["paradigm_assumption_violated"]:
        # 检查是否有任何方法松弛了该假设
        relaxing_methods = get_head_entity(loader, "relaxes", assumption_id)
        if len(relaxing_methods) == 0:
            # 没有任何方法松弛该假设 → 这是真正的技术天花板
            paradigm_failure["ceiling_confirmed"] = True
            paradigm_failure["ceiling_evidence"] = f"No method in KG has relaxes edge to assumption {assumption_id}"
        else:
            # 有方法尝试松弛，但仍未完全解决 → 天花板正在被挑战
            paradigm_failure["ceiling_confirmed"] = False
            paradigm_failure["boundary_challengers"] = [m["id"] for m in relaxing_methods]
```

综合范式缺陷分析，给出对当前技术路线的「天花板评估」：
- 当前范式理论上可能达到的最高性能区间（基于现有最优方法+消除工程缺陷的估算）
- 突破天花板所需的范式变革方向（链接到 A1.5-c 的范式转移推导）

### Step 5: 对抗验证步骤（输出前必须执行）

**为什么需要对抗验证**：宣称「范式级失败」是强结论，容易过度归纳。对抗验证的任务是：对每个声称的范式级失败，主动寻找反例——是否有论文已经解决了它？

```python
for claimed_paradigm_failure in paradigm_level_failures:
    # 将该失败转化为 problem 节点（如果 KG 中有对应 problem）
    failure_problem_id = map_limitation_to_problem(claimed_paradigm_failure["id"])

    if failure_problem_id:
        # 找到声称解决该问题的方法
        addressing_methods = get_head_entity(loader, "addresses", failure_problem_id)
        if len(addressing_methods) > 0:
            # 存在反例！该「范式级失败」可能已被解决
            # 需要进一步验证这些方法是否真正解决了问题，还是仅在特定子集上
            for method in addressing_methods:
                verification_snippets = search_paper_sections(
                    paper_cards_root="paper_cards/parsed",
                    query=f"solves|addresses|overcomes {claimed_paradigm_failure['description']}",
                    paper_ids=[get_evidence_papers(loader, method["id"])],
                    topk=3
                )
            # 如果有实验验证的解决方案 → 降级为 "mixed" 或 "implementation_level"
```

**决策规则**：若对抗验证找到有实验支撑的解决方案，该失败模式必须从「范式级」降级，并在报告中明确标注降级原因。

### Step 6: 原文溯源验证

对所有分析结论中引用的证据，使用 `search_paper_sections` 工具在 `paper_cards/parsed/` 中精确定位原文片段：

```python
snippets = search_paper_sections(
    paper_cards_root="paper_cards/parsed",
    query="<分析结论的关键词>",
    paper_ids=[<涉及的paper_id列表>],
    topk=3
)
```

每条关键结论必须附带：
- `paper_id`：来源论文ID（对应 `knowledge_graph/nodes/papers.json` 中的记录）
- `section`：原文章节标题
- `paragraph_snippet`：原文片段（≥20字，直接引用，禁止改写）
- `score`：语义相似度分值

**无法找到原文片段支撑的结论必须标注 `evidence: unverified`，不得作为最终结论输出。**

## Key Rules

- **「范式缺陷」判定必须满足：≥ 2 篇不同技术实现的论文独立报告了该失败模式**，单一论文的局限性不得标记为范式缺陷。
- **KG limitation 节点优先**：失败实例的枚举必须先执行 `get_entity_by_type(loader, "limitation")`，再补充 Paper Cards 文本提取；不得跳过 KG 结构。
- 「范式假设被违反」的声明需要明确指出该假设是什么，以及为何在该失败场景下假设不成立。
- 天花板评估中的性能上限估算必须基于现有最佳方法的实验数据，不得给出无根据的具体数值。
- 若某方法的 Limitation 章节明确声明某局限「未来可通过 X 解决」，则该局限应标注为 `implementation_level`，不得因该方法存在局限就标记为范式缺陷。
- 「突破天花板的范式变革方向」必须链接到 A1.5-c 已识别的跨域概念，不得独立构造新的范式预测。
- **对抗验证是强制步骤**：对每个声称「范式级」的失败，必须执行 `get_head_entity(loader, "addresses", failure_problem_id)` 检查，找到反例则必须降级并说明。
- **认知坐标纪律**：天花板的客观证据是「某个被所有受影响方法共同 requires 的 assumption 节点没有任何 relaxes 边」——若无此结构证据，天花板结论必须标注为 `speculative`。
