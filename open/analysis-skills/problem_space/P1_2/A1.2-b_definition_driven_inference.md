# Skill: A1.2-b 定义驱动的逻辑推演

**层级**：P1.2 认知框架层 · Conceptualization & Taxonomy  
**RQ类型**：怎么划分？（关系建模 · 因果链）  
**元认知逻辑**：提取核心概念的形式化定义，从定义的数学/逻辑约束出发，推演该约束如何决定问题实体间的必然关联结构，将直觉性归类提升为公理性推导。  
**认知基准面**：将问题空间视为一个由形式化定义派生的公理系统——所有问题之间的关系都是定义约束的逻辑后果，而非经验观察；分析任务是从公理出发演绎，而非从现象出发归纳。

---

## Goal

找到研究对象领域中的核心形式化定义（如公平性公式、隐私预算、安全定义），从定义的逻辑约束出发，推演 KG Problem Space 中哪些问题类别在本质上是同一公理的不同实例，哪些问题之间存在逻辑蕴含关系。

---

## Inputs

- `knowledge_graph/nodes/concept_nodes.json` — KG 中的概念/定义节点，需含 `formal_definition` 字段
- `knowledge_graph/nodes/problems.json` — KG Problem 节点
- `knowledge_graph/edges/` — `instantiates` / `violates` / `implies` 类型边
- `paper_cards/parsed/` — 论文原文，用于提取 Formalization / Definition 章节
- `analyze_report/design_report.md` — RQ 定义

---

## Execution Steps

### Step 1: 精确定位核心形式化定义

**为什么**：形式化定义的精度决定后续推演的可靠性。数学定义（含量词、符号）和定性描述具有本质不同的推演效力，必须区分。

首先，用精确模式词在文献中搜索形式化定义的语言标志：

```python
# 搜索数学定义的语言标志
formal_def_snippets = search_paper_sections(
    paper_cards_root="paper_cards/parsed",
    query="formally defined as we define let denote definition",
    paper_ids=all_paper_ids,
    topk=20
)

# 进一步筛选：区分数学定义和定性定义
mathematical_defs = []
qualitative_defs  = []

for snippet in formal_def_snippets:
    text = snippet.paragraph_snippet
    # 数学定义的标志：含有 ∀, ∃, →, ∈, ≤, ≥, max, min, Pr[·], 或 LaTeX 公式标记
    has_math_symbols = any(sym in text for sym in ["∀", "∃", "→", "∈", "≤", "≥", "Pr[", "\\forall", "\\exists", ":="])
    
    if has_math_symbols:
        mathematical_defs.append({
            "paper_id": snippet.paper_id,
            "section": snippet.section,
            "expression": text,
            "definition_type": "mathematical"
        })
    else:
        qualitative_defs.append({
            "paper_id": snippet.paper_id,
            "section": snippet.section,
            "expression": text,
            "definition_type": "qualitative"
        })
```

同时，从 KG concept_nodes 中获取已结构化的定义节点：

```python
concept_nodes = get_entity_by_type(loader, "Concept")
for c in concept_nodes:
    if c.attributes.get("formal_definition"):
        # 已有结构化定义，直接使用
        formal_defs_from_kg.append(c)
    else:
        # 从 description 字段中提取定义内容
        desc = c.description
```

统计每个定义被多少篇论文引用（高引用 = 高核心度）。若多篇论文对同一概念有不同形式化定义，**必须并列呈现**，不得选择性采纳。

**若文献无形式化定义，仅有自然语言描述，必须标注 `definition_type: qualitative`，后续推演仅为定性逻辑，不构成数学证明。**

### Step 2: 分析定义约束对问题分类的蕴含

**为什么**：形式化定义的每一个变量和约束条件，在被违反时都对应一类特定的问题。这种映射关系是逻辑必然，而非经验归纳——这是「定义驱动推演」与普通分类分析的本质区别。

对每个核心形式化定义 D，系统地分析其约束结构：

```python
for defn in core_definitions:
    # 分析定义 D 的约束空间
    constraint_analysis = judge(
        f"Given this formal definition: '{defn.formal_expression}'\n"
        f"1. List all variables/parameters in the definition.\n"
        f"2. For each variable/condition, what Problem necessarily arises when it is violated?\n"
        f"3. Do different parameter configurations (e.g., large vs small ε) correspond to "
        f"   different severity levels of the same Problem?\n"
        f"4. Does the definition logically entail any inclusion/exclusion relationships "
        f"   between Problem categories? Show the logical steps."
    )
    
    # 从约束分析中提取：
    # - 约束违反 → 必然产生的问题类别
    # - 参数配置 → 问题严重程度的映射
    # - 定义内在的问题类别包含/互斥关系
```

注意区分两种蕴含：
- **强蕴含**：在数学定义的约束下，逻辑上必然成立（可展示推导步骤）
- **弱蕴含**：在定性描述的语境下，语义上大概率成立（需标注 `inference_strength: weak`）

**禁止将自然语言的「因为...所以...」直接等同于数学的蕴含关系（`→`）。**

### Step 3: 将 KG Problem 节点与定义关联

**为什么**：KG 中的 `violates` / `instantiates` 边可能不完整。通过语义搜索补全关联，确保每个 Problem 节点都被纳入定义驱动的分析框架。

```python
for p in get_entity_by_type(loader, "Problem"):
    # 优先读取 KG 中已有的 violates/instantiates 边
    violated_defs   = get_head_entity(loader, "violates", p.id)
    instantiated_defs = get_head_entity(loader, "instantiates", p.id)
    
    existing_links = [(d, "violates") for d in violated_defs] + \
                     [(d, "instantiates") for d in instantiated_defs]
    
    # 若 KG 边缺失，通过语义搜索补全
    if not existing_links:
        # 在来源论文中搜索该问题与已知定义的关联
        source_papers = get_evidence_papers(loader, p.id)
        for defn in core_definitions:
            link_evidence = search_paper_sections(
                query=f"{p.description[:80]} {defn.name} violates satisfies",
                paper_ids=[sp.id for sp in source_papers],
                topk=2
            )
            if link_evidence:
                existing_links.append((defn, "inferred_from_text", link_evidence[0]))
    
    # 验证：该 Problem 是否是定义约束被违反的实例
    # 是否存在多个 Problem 节点对应同一定义约束的不同场景（语义聚合）
```

对 `origin_paper_id` 为 null 的 Problem 节点，先调用 `get_evidence_papers(loader, p.id)` 补全来源，再执行上述关联操作。

### Step 4: 构建定义驱动的关系图

**为什么**：以形式化定义为中心的关系图揭示了问题空间的深层逻辑结构——哪些问题在本质上是同一约束的不同表现，哪些问题之间存在逻辑蕴含（解决一个自动解决另一个）。

```python
# 构建以定义为中心节点、Problem 为叶节点的有向图
relation_graph = {
    "definition_nodes": [],
    "problem_nodes": [],
    "edges": []  # (definition_id, problem_id, relation_type)
}

# 从 Step 3 的关联结果填充图
for p_id, links in problem_definition_links.items():
    for defn, rel_type, *evidence in links:
        relation_graph["edges"].append({
            "from": defn.id,
            "to": p_id,
            "type": rel_type,  # violates | instantiates | implies
            "inference_strength": "strong" if rel_type != "inferred_from_text" else "weak",
            "evidence": evidence[0] if evidence else None
        })

# 从图中推导问题间的必然关系
# 若 Problem_A 和 Problem_B 都 violates 同一定义约束的不同参数配置 → 它们是同类问题的不同实例
# 若 Problem_A 违反约束 C1，Problem_B 违反约束 C2，且 C1 → C2（定义内蕴含） → Problem_A implies Problem_B
```

### Step 5: 对抗性验证：检验推演链的逻辑完整性

**为什么**：定义驱动推演最常见的错误是「跳步」——跳过中间推导步骤直接声明结论。必须主动检查每一条推演链是否存在未证明的跳步。

对每条推演出的问题间必然关系，执行以下检验：

```python
for implied_relation in implied_problem_relations:
    # 展示完整的推导链
    derivation_steps = judge(
        f"Verify this logical claim step by step:\n"
        f"Definition: {implied_relation.derived_from_definition}\n"
        f"Claim: Problem '{implied_relation.problem_a}' implies Problem '{implied_relation.problem_b}'\n"
        f"Show each logical step. If any step requires an assumption not in the definition, "
        f"flag it as 'external_assumption'."
    )
    
    # 检查是否存在 external_assumption
    if "external_assumption" in derivation_steps:
        implied_relation.inference_strength = "weak"
        implied_relation.assumptions = extract_assumptions(derivation_steps)
    
    # 寻找反例：是否存在一个 Problem_A 实例，但不导致 Problem_B？
    counterexample_search = search_paper_sections(
        query=f"{implied_relation.problem_a} without {implied_relation.problem_b}",
        paper_ids=all_paper_ids,
        topk=3
    )
    if counterexample_search:
        implied_relation.counterexample = counterexample_search[0]
        implied_relation.inference_strength = "refuted"
```

所有 `inference_strength: refuted` 的关系必须从最终输出中移除或标注为反例证伪。

### Step 6: 原文溯源验证

对所有分析结论中引用的证据，使用 `search_paper_sections` 工具在 `paper_cards/parsed/` 中精确定位原文片段：

```python
snippets = search_paper_sections(
    paper_cards_root="paper_cards/parsed",
    query="<分析结论的关键词>",
    paper_ids=[<涉及的paper_id列表>],
    topk=3
)
```

每条关键结论必须附带：
- `paper_id`：来源论文ID（对应 `knowledge_graph/nodes/papers.json` 中的记录）
- `section`：原文章节标题
- `paragraph_snippet`：原文片段（≥20字，直接引用，禁止改写）
- `score`：语义相似度分值

**无法找到原文片段支撑的结论必须标注 `evidence: unverified`，不得作为最终结论输出。**

## Key Rules

- **若文献无形式化定义，必须标注 `definition_type: qualitative`**，所有推演结论降级为「逻辑推断」，不可表述为「数学证明」。
- 定义蕴含关系的推演必须展示完整的逻辑推导步骤，不可直接声明结论；跳步必须标注 `external_assumption`。
- `evidence_paper` 字段必须指向具体论文的具体章节（如 `paper_id, Section 3.1`），不得泛指整篇文章。
- 若多篇论文对同一概念有不同的形式化定义，必须并列呈现，并分析定义差异对问题分类结论的影响，不得选择性采纳某一版本。
- 禁止将自然语言的「因为...所以...」直接等同于数学的蕴含关系（`→`）。
- 形式化定义的搜索必须使用精确模式词（"formally defined as"、"we define"、"let X denote"），并区分数学符号（∀, ∃, →）与定性描述，两类定义的推演效力必须在报告中明确区分。
- **认知基准面纪律**：分析的核心逻辑方向是「从定义演绎到问题关系」，而非「从问题观察归纳到定义」；整个分析过程中不得用归纳结论替代演绎推导，若发现某关系只能归纳得到而无法从定义演绎，必须降级为 `inference_strength: weak`。
