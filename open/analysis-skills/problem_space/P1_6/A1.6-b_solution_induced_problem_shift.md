# Skill: A1.6-b 解药诱导的「问题位移」识别

**层级**：P1.6 对抗演化与次生灾害层 · [V3 新增]  
**RQ类型**：问题如何被解法「逼」着进化？（次生灾害 / 补偿性风险）  
**元认知逻辑**：识别因引入某解决方案而「被牺牲」或「新暴露」的安全/隐私属性，构建「解法 → 副作用 → 次生问题」的因果链，评估次生灾害是否构成比原问题更高的风险。  
**认知基准面**：以「解法假设违反的次生问题外推」为透镜——解法的副作用根植于其隐含假设；当解法被部署到假设不成立的场景时，次生问题不可避免地涌现；因此分析重心是「解法依赖什么假设」以及「这些假设在哪些场景下被违反」，而非简单列举已知副作用。

---

## Goal

系统性地审查 Solution Space 中各解决方案的副作用，识别「引入解法 D → 导致新问题 P'」的位移链，并评估 P' 的危害等级，为 Solution Space 的安全性评估提供 Problem Space 视角的反馈。

---

## Inputs

- `knowledge_graph/nodes/methods.json` — KG 方法/解法节点
- `knowledge_graph/nodes/problems.json` — KG Problem 节点（含原始问题和次生问题）
- `knowledge_graph/edges/` — `introduces` / `addresses` / `trades_off` / `reduces_but_exposes` / `requires` / `has_limitation` 类型边
- `paper_cards/parsed/` — Paper Cards，重点提取 Security Analysis / Limitations / Side Effects 章节
- `working_memory/rq_{id}/A1.6-a_coevolution_report.json`（可选）— 攻防演化结果

---

## Execution Steps

### Step 1: 从 assumption 节点出发识别副作用根源

**认知目标**：副作用分析不应从「已知的副作用列表」出发（这会遗漏未被明确讨论的副作用），而应从「解法的假设」出发——当假设被违反时，副作用必然出现。KG 的 `assumption` 节点和 `requires` 边正是对解法前提条件的结构化编码，是副作用根源的系统性来源。

```python
all_assumptions = get_entity_by_type(loader, "assumption")
all_methods = get_entity_by_type(loader, "method")

# 对每个方法，获取其依赖的 assumption 节点
for method in all_methods:
    method_id = method["node_id"]
    
    # requires 边指向该方法依赖的假设/前提
    required_assumptions = get_tail_entity(loader, "requires", method_id)
    # has_limitation 边指向该方法已知的失效模式
    known_limitations = get_tail_entity(loader, "has_limitation", method_id)
    
    method["required_assumptions"] = required_assumptions
    method["known_limitations"] = known_limitations
```

同时，从 Paper Cards 中检索明确讨论副作用的解法：

```python
# 检索 Security Analysis / Limitation / Discussion 中的副作用描述
side_effect_hits = search_paper_sections(
    paper_cards_root="paper_cards/parsed",
    query="solution introduces new attack surface side effect trade-off",
    topk=10
)
deployment_risk_hits = search_paper_sections(
    paper_cards_root="paper_cards/parsed",
    query="while improving security A reduces privacy B exposes vulnerability",
    topk=10
)
```

**位移后的问题必须有文献中的安全分析章节支撑，禁止 AI 臆测副作用。**

### Step 2: 构建「问题位移」三元组

**认知目标**：三元组的构建有两条路径——「KG 结构路径」（`requires` 边 + `has_limitation` 边 → 对应的 problem 节点）和「文本路径」（Paper Cards 中的副作用描述）。两条路径互为补充：KG 路径覆盖已被结构化的副作用，文本路径覆盖仅在叙述中出现的副作用。

**路径 A：KG 结构路径**

```python
for method in methods_with_assumptions:
    method_id = method["node_id"]
    
    # 从 limitation 节点映射到次生 problem 节点
    for limitation in method["known_limitations"]:
        limitation_id = limitation["node_id"]
        limitation_text = limitation.get("description", "")
        
        # 检查该 limitation 是否对应一个 problem 节点（即 limitation 导致了新问题）
        secondary_problem_candidates = get_candidate_entity(
            loader, limitation_text, "problem"
        )
        # 若找到匹配，构建位移三元组
        for candidate in secondary_problem_candidates:
            if candidate["score"] > 0.6:
                shift_triple = {
                    "solution_id": method_id,
                    "solution_name": method.get("canonical_name"),
                    "original_problem_id": get_addressed_problem(loader, method_id),
                    "secondary_problem_id": candidate["node_id"],
                    "secondary_problem_description": candidate["description"],
                    "shift_mechanism": f"limitation '{limitation_text}' leads to '{candidate['description']}'",
                    "shift_path": "kg_structural"
                }
```

**路径 B：文本路径**

```python
for hit in side_effect_hits + deployment_risk_hits:
    # 从 hit 中提取「解法 D → 副作用 → 新问题 P'」的三元组
    # hit["paper_id"], hit["section"], hit["text"] 提供完整溯源
    if hit["score"] > 0.55:
        # 验证 hit 中的解法是否在 KG 中有对应节点
        solution_candidate = get_candidate_entity(
            loader, hit["method_mention"], "method"
        )
        secondary_problem_candidate = get_candidate_entity(
            loader, hit["side_effect_mention"], "problem"
        )
```

对每个有副作用的解法 D，完整构建：
- **原始问题** P：D 被设计来解决的问题（通过 `addresses` 边确认）
- **次生问题** P'：D 的副作用引入的新问题
- **位移机制**：D 的哪个设计决策（来自 `requires` 的哪个假设被违反）导致了 P'

### Step 3: 评估次生灾害严重性

**认知目标**：次生灾害的严重性评估必须与原始问题使用同一评估框架——否则「次生灾害是否超过原问题」的比较就没有意义。A1.4-a 的多维影响分析框架是此处的规范参照，使用一致的维度和评级标准。

```python
for triple in problem_shift_chains:
    original_problem_id = triple["original_problem_id"]
    secondary_problem_id = triple["secondary_problem_id"]
    
    # 从 A1.4-a 报告中查找原始问题和次生问题的影响评级
    if a1_4a_report_exists:
        original_severity = get_max_severity_from_report(
            a1_4a_report, original_problem_id
        )
        secondary_severity = get_max_severity_from_report(
            a1_4a_report, secondary_problem_id
        )
    else:
        # 独立评估，使用相同的评级标准
        harm_data = search_paper_sections(
            paper_cards_root="paper_cards/parsed",
            query=f"{triple['secondary_problem_description']} impact severity damage",
            topk=3
        )
    
    # 净风险变化判断
    triple["severity_comparison"] = {
        "original_severity": original_severity,
        "secondary_severity": secondary_severity,
        "net_risk_change": (
            "worsened" if secondary_severity > original_severity
            else "improved" if secondary_severity < original_severity
            else "neutral"
        )
    }
```

### Step 4: 识别「恶性循环」解法

**认知目标**：恶性循环链的价值在于揭示「解法空间的拓扑陷阱」——某些问题域在当前技术范式下没有「最终解法」，只有「问题形态的持续演变」。识别这类链是 P1.6 层最重要的洞察之一，但必须基于 KG 中已存在的节点和边，不得凭逻辑构造假设性循环链。

```python
# 检测链式结构：解法 D → 次生问题 P' → 新解法 D' → 再生问题 P'' → ...
vicious_cycles = []
for triple in problem_shift_chains:
    secondary_problem_id = triple["secondary_problem_id"]
    # 找到 addresses secondary_problem 的方法（即针对次生问题的新解法）
    remedies_for_secondary = get_head_entity(loader, "addresses", secondary_problem_id)
    
    for new_solution in remedies_for_secondary:
        new_solution_id = new_solution["node_id"]
        # 检查新解法是否也有次生问题
        new_secondary = get_tail_entity(loader, "has_limitation", new_solution_id)
        if new_secondary:
            # 构成二级链：D → P' → D' → P''
            vicious_cycles.append({
                "chain": [
                    triple["solution_id"],
                    secondary_problem_id,
                    new_solution_id,
                    new_secondary[0]["node_id"]
                ],
                "description": f"{triple['solution_name']} → {triple['secondary_problem_description']} → ..."
            })
```

**「恶性循环」链的识别必须基于 KG 中已存在的节点和边，不得凭逻辑构造假设性循环链。**

### Step 5: 向 B2.4-d 输出反馈

将识别到的次生灾害列表输出，供 Solution Space 的 B2.4-d「解药-痛点覆盖率审计」使用（高风险解法权重折半）。

高风险解法判定标准：`net_risk_change == "worsened"` 或参与恶性循环链。

推送内容必须携带完整的 `evidence_paper`、`shift_mechanism` 和 `secondary_problem_id`，B2.4-d 不得凭引用本报告即降低解法评分。

### Step 5a: 对抗性验证「得不偿失」判定

**认知目标**：「次生灾害超过原问题」是强主张，需要反向检验：是否有论文认为该解法整体上仍然是净收益？若有文献明确声称该解法的收益大于副作用，则「得不偿失」的判定需要在报告中呈现双方论据，而非单方面声明。

```python
for triple in worsened_triples:
    solution_id = triple["solution_id"]
    solution_name = triple.get("solution_name", "")
    
    # 检索是否有论文认为该解法整体仍然值得部署
    net_benefit_evidence = search_paper_sections(
        paper_cards_root="paper_cards/parsed",
        query=f"{solution_name} overall benefit outweighs risk worth deploying",
        topk=3
    )
    if net_benefit_evidence and max(s["score"] for s in net_benefit_evidence) > 0.6:
        triple["net_benefit_counter_evidence"] = net_benefit_evidence[0]
        triple["verdict"] = "disputed"  # 存在反驳证据，双方论据并列呈现
    else:
        triple["verdict"] = "worsened_confirmed"
```

### Step 6: 原文溯源验证

对所有分析结论中引用的证据，使用 `search_paper_sections` 工具在 `paper_cards/parsed/` 中精确定位原文片段：

```python
snippets = search_paper_sections(
    paper_cards_root="paper_cards/parsed",
    query="<分析结论的关键词>",
    paper_ids=[<涉及的paper_id列表>],
    topk=3
)
```

每条关键结论必须附带：
- `paper_id`：来源论文ID（对应 `knowledge_graph/nodes/papers.json` 中的记录）
- `section`：原文章节标题
- `paragraph_snippet`：原文片段（≥20字，直接引用，禁止改写）
- `score`：语义相似度分值

**无法找到原文片段支撑的结论必须标注 `evidence: unverified`，不得作为最终结论输出。**

## Key Rules

- **次生问题必须有文献的 Security Analysis 章节明确讨论**，或通过 KG `has_limitation` 边 + `get_candidate_entity` 映射得出，禁止 LLM 自行推断「引入该解法可能会...」类型的副作用。
- 严重性对比（`severity_comparison`）必须基于 A1.4-a 的多维影响分析框架，使用一致的评级标准，不得主观比较；若 A1.4-a 不可用，标注 `severity_source: independent_estimate`。
- 「恶性循环」链的识别必须基于 KG 中已存在的节点和边，不得凭逻辑构造假设性循环链。
- 若某解法在 Paper Cards 中无任何 Security Analysis 章节，必须标注 `security_analysis: absent`，不得将该解法标记为无副作用。
- 高风险解法推送到 B2.4-d 时必须携带完整的 `evidence_paper` 和 `shift_mechanism`，B2.4-d 不得凭引用本报告即降低解法评分。
- **认知坐标纪律**：`get_tail_entity(loader, "requires", method_id)` 获取假设节点是副作用根源分析的第一步，而非从已知副作用列表反向推理；优先级：KG 结构路径 > 文本证据路径。
