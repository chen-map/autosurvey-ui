# Skill: A1.3-b 因果链溯源（痛点-解药）

**层级**：P1.3 深层动因层 · Rationale & Root Causes  
**RQ类型**：为什么？（采用动机）  
**元认知逻辑**：先系统性地撕开旧方法的「伤口」，再证明新方法恰好是对应的「解药」，建立「旧痛点 → 新能力」的强对齐映射，解释技术演进的必然性。  
**认知基准面**：以「否定结构驱动的技术演进溯源」为透镜——痛点不是笼统的「性能不足」，而是文献中白纸黑字出现的否定词结构；解药不是泛泛的新技术，而是与该否定结构在逻辑上构成互补的具体能力。

---

## Goal

从 KG 和 Paper Cards 中提取旧方法的核心缺陷，并对照提取新方法/新范式的核心能力，构建严格对齐的「痛点-解药」映射表，为 RQ 提供技术采用动机的因果解释。

---

## Inputs

- `knowledge_graph/nodes/methods.json` — KG 中的方法/技术节点（含 old/new 时代标签）
- `knowledge_graph/nodes/problems.json` — Problem 节点中属于「旧方法局限性」类的节点
- `knowledge_graph/edges/` — `addresses` / `improves_over` / `replaces` / `motivated_by` 类型边
- `paper_cards/parsed/` — Paper Cards，重点提取 Introduction 的两段式结构（旧方法成功段 + 旧方法失败段）
- `analyze_report/design_report.md` — RQ 定义

---

## Execution Steps

### Step 1: 提取旧方法痛点清单

**认知目标**：痛点必须来自论文中的「否定词结构」——这是作者对旧方法失败的明确宣告，不是 AI 的推断。找到这些否定结构就是找到领域公认的技术演进动力。

使用 KG 的语义检索和文本检索双轨并行：

**轨道 A：KG 否定语义边检索**

```python
all_problems = get_entity_by_type(loader, "problem")
# 筛选 description 中含局限性语义的 problem 节点
limitation_problems = get_entity_by_constraint(
    all_problems, "description", "contains", "fail"
)
# 同样筛选 "cannot", "limited", "insufficient", "unable"
```

**轨道 B：Paper Cards 否定结构检索**

```python
# 检索 Introduction 章节中的否定词结构
negation_hits_1 = search_paper_sections(
    paper_cards_root="paper_cards/parsed",
    query="however existing methods fail to",
    topk=10
)
negation_hits_2 = search_paper_sections(
    paper_cards_root="paper_cards/parsed",
    query="but prior work cannot",
    topk=10
)
# 补充其他否定词
negation_hits_3 = search_paper_sections(
    paper_cards_root="paper_cards/parsed",
    query="unfortunately previous approaches struggle with",
    topk=5
)
negation_hits_4 = search_paper_sections(
    paper_cards_root="paper_cards/parsed",
    query="traditional methods are limited by",
    topk=5
)
```

对每条命中的否定结构，提取：
- 痛点的「受害维度」（accuracy / efficiency / scalability / generalization / security 等）——必须是论文中明确描述的具体属性
- 该痛点被多少篇不同论文提及（高频 ≥ 3篇 = 领域共识痛点）

### Step 2: 将痛点文本映射到 KG problem 节点

**认知目标**：将自然语言痛点与 KG 中结构化的 problem 节点对齐，使后续的解药检索可以沿 KG 边进行，而非仅依赖文本匹配。

对 Step 1 中每个痛点文本，使用 `get_candidate_entity` 在 KG 中定位对应的 problem 节点：

```python
for painpoint_text in painpoint_list:
    candidate_nodes = get_candidate_entity(loader, painpoint_text, "problem")
    # candidate_nodes 按相似度排序，取 top-1 或人工确认
    # 记录 node_id, canonical_name, description, confidence
```

若 `get_candidate_entity` 返回空结果，说明该痛点尚未在 KG 中结构化——标注为 `kg_node: absent`，仍可基于文本检索进行后续分析，但需在报告中声明证据强度降低。

若找到的 problem 节点的 `origin_paper_id` 为 null，调用 `get_evidence_papers(loader, node_id)` 确认其多论文支撑。

### Step 3: 构建痛点-解药对齐映射

**认知目标**：解药不是「新方法」，而是「恰好覆盖该痛点受害维度的新能力」。对齐验证必须同时满足三个条件：语义互补、逻辑覆盖、文献明确联系。

对每个高频痛点对应的 KG problem 节点，沿边反向查找「解药」方法节点：

```python
# 找到 addresses 该 problem 的方法节点（即解药候选）
remedy_method_nodes = get_head_entity(loader, "addresses", problem_id)
```

对每个 remedy_method_node，验证对齐有效性：

- **语义对齐**：痛点的「受害维度」与解药的 `description` 字段中「受益维度」必须对应（如痛点是 `false positive rate`，解药的 description 必须提及 precision/recall 改进）
- **逻辑互补**：痛点描述的失败条件必须被解药的能力覆盖（非部分覆盖）
- **文献支撑**：检查 `get_head_entity` 返回边的 `evidence` 字段，至少一篇 `context_paper_id` 明确将该痛点作为研究动机

```python
# 验证解药是否是在痛点论文之后出现的（方向性验证）
extends_edges = get_relation(loader, remedy_method_id, "out")
extends_to_older = [e for e in extends_edges if e["edge_type"] == "extends"]
# extends 边应指向旧范式方法节点，验证演进方向正确
```

同时检查该解药的 `extends` 类型出边是否指向被痛点描述的旧方法——这确认了「新方法是对旧方法的直接回应」。

对齐类型判定：
- `direct`：解药完全覆盖痛点维度且有实验验证
- `partial`：仅部分覆盖或仅有定性论证
- `claimed_only`：论文声称解决但无实验验证（必须突出标注）

### Step 4: 识别未被解决的痛点（Gap）

**认知目标**：「开放痛点」是未来研究机会的直接指示器，同时也是 A1.5 层盲区分析的强输入。发现它们的方式不是随意列举，而是系统性地遍历高频否定词命中后检查 `get_head_entity` 返回为空的 problem 节点。

```python
for problem_id in high_frequency_painpoint_ids:
    remedies = get_head_entity(loader, "addresses", problem_id)
    if len(remedies) == 0:
        # 这是开放痛点——在 KG 中有 problem 节点但无任何方法 addresses 它
        open_painpoints.append(problem_id)
```

对每个开放痛点，分析「为何尚未被解决」——依据必须来自文献的 Limitation 或 Future Work 章节：

```python
unresolved_reason = search_paper_sections(
    paper_cards_root="paper_cards/parsed",
    query="[painpoint_description] challenge open problem future work",
    topk=5
)
```

开放痛点列表作为输出推送至 A1.5 Gap 分析层。

### Step 5: 输出报告

汇总所有痛点-解药对的对齐结果，构建完整的映射表，标注各项的对齐类型、证据强度、来源论文。

### Step 6: 原文溯源验证

对所有分析结论中引用的证据，使用 `search_paper_sections` 工具在 `paper_cards/parsed/` 中精确定位原文片段：

```python
snippets = search_paper_sections(
    paper_cards_root="paper_cards/parsed",
    query="<分析结论的关键词>",
    paper_ids=[<涉及的paper_id列表>],
    topk=3
)
```

每条关键结论必须附带：
- `paper_id`：来源论文ID（对应 `knowledge_graph/nodes/papers.json` 中的记录）
- `section`：原文章节标题
- `paragraph_snippet`：原文片段（≥20字，直接引用，禁止改写）
- `score`：语义相似度分值

**无法找到原文片段支撑的结论必须标注 `evidence: unverified`，不得作为最终结论输出。**

## Key Rules

- **痛点提取必须来自 Paper Cards 的 Introduction 章节否定结构**，禁止 LLM 凭先验知识捏造痛点；否定词结构检索必须使用 `search_paper_sections` 工具执行，不得人工推断。
- `alignment_type: claimed_only` 表示论文宣称解决该痛点但无实验证明，此类对齐必须在报告中突出标注，不得等同于 `direct` 对齐。
- 痛点的「受害维度」必须是文献中明确描述的具体属性（如 `false positive rate`），禁止用模糊词汇（如「性能不好」）。
- 开放痛点必须附带「为何尚未被解决」的分析，分析依据必须来自文献的 Limitation 或 Future Work 章节。
- 若新方法与旧方法属于完全不同的技术范式（如规则系统 → 深度学习），需在报告中说明范式断层，不可将不同范式的能力直接做对齐比较。
- **认知坐标纪律**：`get_head_entity(loader, "addresses", problem_id)` 返回为空是开放痛点的客观判定标准，不得用文本检索结果「补全」解药来规避空结果。
