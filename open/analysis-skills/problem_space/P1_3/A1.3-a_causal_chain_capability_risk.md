# Skill: A1.3-a 因果链溯源（能力-风险）

**层级**：P1.3 深层动因层 · Rationale & Root Causes  
**RQ类型**：为什么？（脆弱性本源）  
**元认知逻辑**：识别系统的核心能力/特性（不可改变的设计属性），建立「具备能力X → 必然暴露风险Y」的强因果映射，论证问题的根因在于系统本质，而非实现缺陷。  
**认知基准面**：以「能力-风险因果链逆推」为透镜——将系统能力视为风险的必然前因，区分「内生性风险」（移除能力则核心功能丧失）与「可缓解风险」（工程选择导致，可替换实现方式规避）。

---

## Goal

从 KG 的系统/技术能力节点出发，对每个核心能力推导其「必然的安全/失效副作用」，建立能力-风险因果映射表，揭示 Problem Space 中问题的不可规避性根源。

---

## Inputs

- `knowledge_graph/nodes/methods.json` — KG 中描述系统能力/技术特性的节点
- `knowledge_graph/nodes/problems.json` — KG Problem 节点
- `knowledge_graph/edges/` — `supports` / `addresses` / `targets` 类型边
- `paper_cards/parsed/` — Paper Cards，提取 Introduction/Motivation 中的因果分析
- `analyze_report/design_report.md` — RQ 定义

---

## Execution Steps

### Step 1: 识别核心能力节点

**认知目标**：找到系统中「不可删除而不损失核心功能」的能力集合——这些才是推导不可规避风险的正确起点。如果起点选错（选了可替换的实现细节），后续所有因果推导都会指向「可缓解风险」而非「内生性风险」。

使用 `get_entity_by_type` 获取所有 method 类型节点，然后按 `description` 字段过滤含能力关键词（如 "capability", "ability", "enables", "allows", "can perform"）的节点：

```python
all_methods = get_entity_by_type(loader, "method")
# 过滤 description 中含核心能力语义的节点
capability_nodes = get_entity_by_constraint(
    all_methods, "description", "contains", "<capability_keyword>"
)
```

对每个候选能力节点，调用 `get_relation(loader, method_id, "out")` 获取其全部出边，筛选 `edge_type` 为 `"addresses"` 或 `"targets"` 且目标节点为 problem 类型的边——这些边即为 KG 编码的能力→风险直接连接。

**选择标准**（同时满足）：
- 被 ≥ 3 篇不同 `context_paper_id` 的边引用（即跨论文共识）
- 在 KG 中有至少 2 条出边指向 problem 节点

若某能力节点的 `origin_paper_id` 为 null，使用 `get_evidence_papers(loader, node_id)` 获取支撑该节点的论文集合，确认其跨论文支撑数量。

### Step 2: 针对每个能力推导必然风险

**认知目标**：从 KG 边的 `evidence` 字段提取因果机制文本，而非凭逻辑推断。KG 中 `addresses` / `targets` 类型边的 `evidence` 字段记录了论文原文对该因果关系的论证文本——这是最直接的机制证据。

对每个核心能力节点 C：

```python
out_edges = get_relation(loader, capability_node_id, "out")
# 筛选指向 problem 节点的因果边
causal_edges = [e for e in out_edges if e["edge_type"] in ["addresses", "targets"]]

for edge in causal_edges:
    # edge["evidence"] 包含因果机制文本
    mechanism_text = edge["evidence"]
    # 获取完整上下文
    context_snippets = search_paper_sections(
        paper_cards_root="paper_cards/parsed",
        query=mechanism_text[:100],  # 用证据文本前100字检索原文
        paper_ids=[edge["context_paper_id"]],
        topk=3
    )
```

分析每个能力的哪个属性（开放性/自主性/不透明性/持久性）构成攻击面或失效点，推导：
- 该风险是能力的「内在属性」——删除该属性则系统核心功能丧失
- 还是「实现缺陷」——可通过工程手段（如输入过滤、访问控制）规避

**推导出的因果链必须在提供的文献集内找到直接论证，不可跨领域主观联想。**

### Step 3: 验证因果强度

**认知目标**：因果强度的差异直接决定风险的可行动性——Strong 强度的因果链支持「问题不可规避」论断，Weak 强度只能支持「问题值得关注」论断。

因果强度必须基于 KG 边的量化属性操作化定义：

- **Strong**：边的 `confidence >= 0.8` **且** 至少来自 2 个不同 `context_paper_id` 的边独立指向同一 capability→problem 对
- **Moderate**：`confidence >= 0.6` **或** 仅 1 篇论文有明确论证（单源支撑）
- **Weak**：`confidence < 0.6`，仅从逻辑推断，无直接文献支撑（必须标注并降低置信度）

若某条因果边缺少 `confidence` 字段，使用 `search_paper_sections` 检索相关论文段落，根据论文中表述的确定性（"we show that" / "we observe that" / "we conjecture that"）手动评级。

### Step 4: 构建能力-风险映射图

以能力节点为源、Problem 节点为目标，构建有向因果图：
- 边标注：`causal_strength`（strong/moderate/weak）、`evidence_paper_id`、`causal_mechanism`（来自 edge `evidence` 字段）
- 若某能力节点在 KG 中无出边指向 Problem 节点，标注 `no_kg_evidence: true`，不得凭 LLM 知识补充因果关系

同时收集能力节点的 `canonical_name`、`description`、`label` 字段用于输出报告的可读性标注。

### Step 5: 识别「不可规避」vs「可缓解」的风险

**认知目标**：「不可规避」的论断是整个 P1.3 层的核心输出——它直接回答了「为什么这些问题不能简单修复」。错误地将「可缓解风险」标注为「不可规避」会导致研究意义虚高；错误地将「内生性风险」标注为「可缓解」会导致研究意义被低估。

分类标准：
- **不可规避（inherent）**：风险来自系统的核心功能属性，只能缓解不能消除
- **可缓解（mitigable）**：风险来自实现层面的选择，通过工程改进可以规避

对每个标注为「inherent」的能力-风险对，执行对抗性验证（见 Step 5a）后才能确认分类。

### Step 5a: 对抗性验证「不可规避」分类

**认知目标**：「不可规避」是强主张，必须经受反驳检验。验证逻辑：若移除该能力，系统核心功能是否确实丧失？若有反例论文声称在不依赖该能力的情况下实现了同等功能，则该风险应降级为「可缓解」。

对每个 inherent 分类，执行：

```python
# 检查是否存在声称在没有该能力的情况下系统仍可运行的论文
counter_evidence = search_paper_sections(
    paper_cards_root="paper_cards/parsed",
    query="without [capability_name] the system cannot",
    topk=5
)
# 同时检索反驳证据
counter_evidence_alt = search_paper_sections(
    paper_cards_root="paper_cards/parsed",
    query="alternative approach avoids [capability_name] while maintaining",
    topk=3
)
```

若 `counter_evidence` 中有 score > 0.6 的命中，且内容表明「系统在无此能力时功能丧失」，则 inherent 分类得到支撑；若发现替代方案证据，则降级为 mitigable 并记录反驳论文。

### Step 6: 原文溯源验证

对所有分析结论中引用的证据，使用 `search_paper_sections` 工具在 `paper_cards/parsed/` 中精确定位原文片段：

```python
snippets = search_paper_sections(
    paper_cards_root="paper_cards/parsed",
    query="<分析结论的关键词>",
    paper_ids=[<涉及的paper_id列表>],
    topk=3
)
```

每条关键结论必须附带：
- `paper_id`：来源论文ID（对应 `knowledge_graph/nodes/papers.json` 中的记录）
- `section`：原文章节标题
- `paragraph_snippet`：原文片段（≥20字，直接引用，禁止改写）
- `score`：语义相似度分值

**无法找到原文片段支撑的结论必须标注 `evidence: unverified`，不得作为最终结论输出。**

## Key Rules

- **因果链必须有文献直接论证**，禁止基于常识推断因果关系，Weak 强度的链必须在报告中突出标注。
- 「能力」节点必须是系统的核心设计属性（非可选特性），否则不构成「不可规避」根因。
- `evidence_section` 字段必须精确到论文的具体章节编号，不允许仅填写 `Introduction`（过于宽泛）。
- 若某能力在 KG 中无出边指向 Problem 节点，不得凭 LLM 知识补充因果关系，应标注 `no_kg_evidence: true`。
- 「不可规避」分类需严格把关：只有当删除该能力会导致系统核心功能丧失时，才可标注为 `inherent`；每个 inherent 分类必须经过 Step 5a 对抗验证后方可确认。
- **认知坐标纪律**：因果强度的 Strong/Moderate/Weak 三级必须严格基于 KG 边的 `confidence` 值和 `context_paper_id` 多样性，禁止主观判断升级强度。
