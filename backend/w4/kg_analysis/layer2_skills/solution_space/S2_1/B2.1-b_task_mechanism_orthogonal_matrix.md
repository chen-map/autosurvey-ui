# Skill: B2.1-b 任务-机制正交矩阵

**层级**：S2.1 方案范式层 · Solution Paradigms & Frameworks  
**RQ类型**：用什么方案？（架构设计）  
**元认知逻辑**：将方法按「任务类型」与「架构类型」两个正交维度构建矩阵，揭示「任务→架构」的适配规律，以及哪些任务-架构组合是空白（研究机会）或热点（成熟区域）。  
**认知基准面**：矩阵中「零密度象限」不等于研究机会——它可能是技术不适配导致的结构性空白；只有当问题节点存在但无对应机制覆盖时，才是真正的研究空白。

---

## Goal

从 KG 的 Method 节点中提取任务目标和技术架构两个维度，构建任务-架构适配矩阵，统计各象限的解法密度，识别最优适配模式和研究空白。

---

## Inputs

- `knowledge_graph/nodes/methods.json` — KG 方法节点，含 `task_type` 和 `architecture_type` 属性
- `knowledge_graph/edges/` — `proposes` 边（论文到方法）、`addresses` 边（方法到问题）
- `paper_cards/parsed/` — Paper Cards，提取 Method 章节的任务定义和架构描述
- `working_memory/rq_{id}/B2.1-a_paradigm_report.json`（可选）— 上游范式分类结果

---

## Execution Steps

### Step 1: 从 KG `addresses` 边提取任务维度标签

**推理目标**：为什么用 `addresses` 边而非方法节点的自身属性？因为方法节点的 `task_type` 字段往往由人工填写，可能缺失或不一致；而 `addresses` 边的尾节点是 `problem` 类型节点，其 `canonical_name` 经过规范化，是更可靠的任务分类来源。

**操作流程**：

获取所有方法节点，然后通过 `addresses` 边获取其指向的 problem 节点：
```python
all_methods = get_entity_by_type(loader, "method")

# 对每个方法，获取其所 addresses 的问题节点
for method in all_methods:
    problem_nodes = get_tail_entity(loader, "addresses", method["node_id"])
    # problem_nodes 的 canonical_name 即为该方法的任务目标描述
```

收集所有 problem 节点的 `canonical_name`，按语义相似度合并同义表达，形成任务标签集（目标：4~8 个标签）。合并标准：若两个 `canonical_name` 的核心动词和操作对象相同，则合并为统一标签。

**决策条件**：若某方法的 `addresses` 边为空（即未连接任何 problem 节点），则从 Paper Card 中推断任务类型，并标注 `task_label: inferred`；若推断也无法完成，标注 `task_label: unspecified`，该方法仍需出现在矩阵中，但归入「任务未知」行。

### Step 2: 从方法 `description` 提取机制维度标签

**推理目标**：机制标签的提取需要区分「架构选择」（Transformer vs GNN vs 符号推理）和「操作范式」（生成式 vs 判别式 vs 搜索式）。两者都是正交矩阵的有效维度，但本步骤聚焦架构类型，因为架构决定了方法的计算模式和所需数据形态。

**操作流程**：

使用 `get_entity_by_constraint` 按关键词过滤方法节点的 description 字段，识别不同机制类型：
```python
# 示例：找出使用图神经网络的方法
gnn_methods = get_entity_by_constraint(
    all_methods, "description", "contains", "graph neural|GNN|graph convolution"
)

# 找出使用 Transformer / 注意力机制的方法
transformer_methods = get_entity_by_constraint(
    all_methods, "description", "contains", "transformer|attention mechanism|BERT|language model"
)

# 找出使用符号/规则推理的方法
symbolic_methods = get_entity_by_constraint(
    all_methods, "description", "contains", "rule-based|symbolic|constraint solving|formal verification"
)

# 找出使用进化/搜索算法的方法
search_methods = get_entity_by_constraint(
    all_methods, "description", "contains", "genetic|evolutionary|search-based|fuzzing|mutation"
)
```

每个方法只归入一个主导机制类别；若关键词匹配到多个类别（混合架构），取 description 中出现频次最高的关键词对应的类别作为主类别，并在附注中记录次要类别。

标签集目标：4~8 个架构类型标签，必须全部来自文献原文中出现的术语。

### Step 3: 构建任务-架构矩阵并计算象限密度

**推理目标**：矩阵填充不是简单的计数——关键在于找到「任务-机制耦合」现象，即某任务类型只有一种机制能覆盖，这意味着该任务对架构有强约束（或该领域存在范式锁定）。

**操作流程**：

对每个（任务类型 T，架构类型 M）组合，计算该象限的方法集合：
```python
task_filtered = [m for m in all_methods if m["task_label"] == T]
mechanism_filtered = [m for m in all_methods if m["mechanism_label"] == M]
cell_methods = intersect(task_filtered, mechanism_filtered)
cell_count = count(cell_methods)
```

象限密度标签：
- `hot`：cell_count ≥ 3 且占该任务行总数 > 50%
- `normal`：cell_count ≥ 2
- `cold`：cell_count = 1
- `empty`：cell_count = 0

**任务-机制耦合识别**：对每一行（任务类型），若所有非零象限集中在同一列（同一机制类型），则该任务存在「范式锁定」——记录 `paradigm_lock: true`，这是重要的发现。

### Step 4: 识别研究空白（零密度象限的二次验证）

**推理目标**：零密度象限的解读需要二阶推理——「该组合不存在」可能是因为：(a) 技术上不可行（如符号推理无法处理自然语言输入），或 (b) 被社区忽视（真正的研究机会）。必须区分这两种情况，否则「研究空白」的声明是不负责任的。

**判断流程**：
- 对每个空白象限（任务 T + 机制 M），检查该任务类型对应的 problem 节点是否有 `has_limitation` 边指向与机制 M 相关的 limitation 节点——若有，说明该空白是已知技术限制，不是忽视
- 若无 `has_limitation` 证据，则该空白是潜在研究机会，标注 `opportunity_type: overlooked`
- 若有 `has_limitation` 证据，标注 `opportunity_type: technical_barrier`，不得声称研究机会

### Step 5: 结合时间维度分析任务-架构演化（可选）

若 A1.1-d 已执行，按年份追踪各矩阵象限的密度变化：

统计每年新增到各象限的方法数，识别趋势：
- 某象限从「冷」变「热」→ 该任务-架构组合在近年受到关注
- 某象限从「热」变「冷」→ 该组合可能被更优方案取代（结合 B2.1-c 数据验证）

### Step 6: 原文溯源验证

对所有分析结论中引用的证据，使用 `search_paper_sections` 工具在 `paper_cards/parsed/` 中精确定位原文片段：

```python
snippets = search_paper_sections(
    paper_cards_root="paper_cards/parsed",
    query="<分析结论的关键词>",
    paper_ids=[<涉及的paper_id列表>],
    topk=3
)
```

每条关键结论必须附带：
- `paper_id`：来源论文ID（对应 `knowledge_graph/nodes/papers.json` 中的记录）
- `section`：原文章节标题
- `paragraph_snippet`：原文片段（≥20字，直接引用，禁止改写）
- `score`：语义相似度分值

**无法找到原文片段支撑的结论必须标注 `evidence: unverified`，不得作为最终结论输出。**

## Key Rules

- **任务类型标签优先来自 `addresses` 边的 problem 节点 `canonical_name`**，其次才从 Paper Card 推断；推断来源必须标注 `inferred`。
- 任务类型和架构类型标签必须来自文献原文，不得由 LLM 构造标签体系。
- 矩阵中每个非零象限必须列出对应论文 ID，不得仅给出计数。
- 「研究机会」的识别（空白象限）必须经过二次验证：区分「技术壁垒空白」和「忽视空白」；未经验证的空白象限不得声称为研究机会。
- 「范式锁定」发现（某任务只对应单一机制）需标注其是领域成熟的标志还是探索不足的标志，两种解读需附对应证据。
- 若某 Method 节点缺少任务类型或架构类型属性，必须从 Paper Card 内容推断并标注 `inferred`，不得跳过该节点。
- 适配规律声明需有统计支撑（如「80% 的检测任务使用 GNN」），不得仅凭少数案例泛化。
- **认知坐标规则**：每次执行在 Checkpoint Output 第一行记录认知坐标，格式为 `[认知坐标: S2.1 · 任务-机制正交映射 · <本次具体分析焦点>]`。
