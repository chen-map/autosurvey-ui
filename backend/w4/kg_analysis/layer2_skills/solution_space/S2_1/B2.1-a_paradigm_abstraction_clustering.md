# Skill: B2.1-a 范式抽象与谱系聚类

**层级**：S2.1 方案范式层 · Solution Paradigms & Frameworks  
**RQ类型**：用什么方案？（技术流派归类）  
**元认知逻辑**：去除具体工具名称的干扰，提取每种方法背后的「底层决策逻辑」（如：基于搜索、基于变异、基于学习、基于规则），将所有解法聚类为互斥的元范式，揭示领域解法的谱系结构。  
**认知基准面**：相同的表面技术标签（如「基于 Transformer 的方法」）可能属于不同的元范式，而不同名称的方法可能共享同一底层决策逻辑——范式判断的依据是「做什么决策、基于什么假设」，不是「用什么工具」。

---

## Goal

从 KG 的 Method/Solution 节点中，提取所有解法的核心决策逻辑，通过聚类分析归纳出 N 个互斥的「元范式」，建立解法谱系树，为 Solution Space 的系统性理解提供顶层分类框架。

---

## Inputs

- `knowledge_graph/nodes/methods.json` — KG 中的方法/解法节点
- `knowledge_graph/edges/` — `proposes` / `extends` / `contradicts` / `compares_with` 类型边
- `paper_cards/parsed/` — Paper Cards，提取 Method 章节的核心动词逻辑
- `knowledge_graph/nodes/papers.json` — 论文元数据（year、venue、authors字段）
- `analyze_report/design_report.md` — RQ 定义

---

## Execution Steps

### Step 1: 提取每个方法的「核心动词逻辑」

**推理目标**：为什么要「去名称化」？因为专有名词（如模型名、工具名）是实现层细节，它们遮蔽了真正的设计决策。范式聚类的信号在于「这个方法在做什么类型的操作」，而不是「用什么工具做操作」。

**操作流程**：

首先，从 KG 获取所有 method 类型节点：
```python
all_methods = get_entity_by_type(loader, "method")
method_paper_ids = [m["context_paper_id"] for m in all_methods]
```

然后，从 Paper Cards 中精确搜索核心机制描述片段——这些片段往往出现在 Method 章节的第一段或系统概述段：
```python
core_mechanism_snippets = search_paper_sections(
    paper_cards_root="paper_cards/parsed",
    query="our method works by|the key idea is|we propose to|the core insight is|our approach",
    paper_ids=method_paper_ids,
    topk=5
)
```

对每个方法节点，执行去名称化：
- 读取节点的 `description` 字段和 `canonical_name` 字段
- 从搜索结果中提取核心操作片段
- 删除所有首字母大写的专有技术词（模型名、工具名、数据集名）
- 保留动词+宾语结构：如「optimize → program」「generate → test cases」「detect → anomalies」「transform → representation」

同时，从 KG 中提取该方法的核心假设（`requires` 边的尾节点揭示了方法运行所依赖的前提条件）：
```python
method_assumptions = get_tail_entity(loader, "requires", method_id)
# 返回 assumption 类型节点，其 canonical_name 描述了方法依赖的前提
```

**决策条件**：若某方法的 `description` 字段少于 30 字，或 `search_paper_sections` 搜索得分 < 0.4，则标注 `verb_logic: underspecified`，需人工补充后再聚类。

**输出格式**（每个方法）：
```
method_id: m_xxx
canonical_name: <原始名称>
stripped_verb_pattern: "<动词> → <操作对象>"
core_assumption: "<来自 requires 边的假设描述>"
evidence_snippet: "<原文片段>"
source_paper_id: "<paper_id>"
```

### Step 2: 基于「动词模式 + 共享假设」聚类为元范式

**推理目标**：为什么必须同时要求「动词模式相似」AND「假设相同」才能归为同一范式？因为两个方法可能都在「搜索」，但一个假设「存在可枚举的状态空间」，另一个假设「存在可微分的目标函数」——这是两种根本不同的世界观，属于不同范式。

**聚类判定规则**：
- 两个方法归为同一元范式，当且仅当：(1) 其 stripped_verb_pattern 语义相似度 > 0.75，AND (2) 其 `requires` 边指向的 assumption 节点具有相同的 `canonical_name` 或语义等价
- 若满足条件 (1) 但不满足条件 (2)，则归为「表面相似但范式不同」——这是需要重点标注的误判陷阱

**操作流程**：
```python
# 获取两个方法的假设集合
assumptions_A = get_tail_entity(loader, "requires", method_id_A)
assumptions_B = get_tail_entity(loader, "requires", method_id_B)
# 取交集判断假设重叠度
shared_assumptions = intersect(assumptions_A, assumptions_B)
```

元范式数量控制在 3~7 个；若聚类结果超过 7 个，需检查是否因 stripped_verb_pattern 粒度太细导致过度分裂，此时应提升抽象层级重新聚类。

**混合架构判定**：若同一论文的多个方法节点分别落入不同元范式，则该论文归为「混合架构」，不得强行归入单一范式。

### Step 3: 验证元范式的文献覆盖与谱系关联

**推理目标**：`extends` 边是天然的谱系信号——若方法 B extends 方法 A，则它们很可能属于同一谱系（A 是祖先，B 是派生）；`contradicts` 边则是范式边界的显式标记。

**操作流程**：

对每个方法节点，获取其所有谱系关联：
```python
method_relations = get_relation(loader, method_id, "both")
# 过滤出 extends 和 contradicts 边
extends_edges = [r for r in method_relations if r["edge_type"] == "extends"]
contradicts_edges = [r for r in method_relations if r["edge_type"] == "contradicts"]
```

`extends` 边构成的连通分量 = 一个自然谱系群（lineage group）。若一个谱系群跨越了两个不同的元范式，需重新审视范式边界是否划定合理。

孤立范式验证：若某元范式仅有 1 篇论文，标注 `single_paper_paradigm: true`。

### Step 4: 建立谱系树与范式关系

**推理目标**：「替代」关系是最强的声明，需要最严格的证据——仅仅时间上更晚出现不足以证明替代，必须有明确的否定性表达。

**分析逻辑**：

**祖先-派生关系**：来自 `extends` 边形成的有向路径。提取 `extends` 边的 `evidence` 字段，该字段记录了改进声明（evolution delta），用于描述派生方法相对于祖先的具体进步。

**互补关系**：若两个不同范式的方法经常同时出现在同一篇论文中（同一 `context_paper_id`），且两个方法节点都由同一篇论文的 `proposes` 边提出，则为互补。

**替代关系**（严格条件，满足其一即可）：
- 条件 A：新方法有 `contradicts` 边指向旧方法/旧范式的代表性方法
- 条件 B：从新方法论文中搜索否定性表达：
```python
negation_snippets = search_paper_sections(
    paper_cards_root="paper_cards/parsed",
    query="unlike previous|in contrast to|fails to handle|cannot address|prior work ignores",
    paper_ids=[newer_paper_id],
    topk=3
)
```
若两个条件均不满足，不得声称替代关系，只记录为「时序共存」。

### Step 5: 识别主流范式与新兴范式

基于论文数量和年份分布（年份来自 `knowledge_graph/nodes/papers.json` 的 `year` 字段）：
- **主流范式**：论文数 Top 2，且时间跨度 > 3 年
- **新兴范式**：近 2 年论文占该范式总论文数 > 60%
- **衰退范式**：近 2 年无新论文，且历史峰值 ≥ 3 篇

溯源验证：对新兴范式，用 `get_evidence_papers(loader, node_id)` 追溯支撑该范式的论文集合，确认年份分布真实可信。

### Step 6: 对抗性验证——边界困难案例审查

**推理目标**：聚类结果最容易在范式边界处出错。对每个范式边界，必须找出「最难分类的论文」并显式为其分类决策辩护，而不是假设聚类结果天然正确。

**操作流程**：
- 对每两个相邻元范式，找出 stripped_verb_pattern 最接近边界（相似度在 0.65~0.80 之间）的方法
- 对该方法，重新检查其 `requires` 边的假设集合，做出明确的归属判断
- 在报告中记录：`boundary_case: true`，`placement_rationale: "<明确的判断理由>"`
- 若判断理由不充分，该方法归为「模糊归属」，在输出中标注 `paradigm_id: ambiguous`

### Step 7: 原文溯源验证

对所有分析结论中引用的证据，使用 `search_paper_sections` 工具在 `paper_cards/parsed/` 中精确定位原文片段：

```python
snippets = search_paper_sections(
    paper_cards_root="paper_cards/parsed",
    query="<分析结论的关键词>",
    paper_ids=[<涉及的paper_id列表>],
    topk=3
)
```

每条关键结论必须附带：
- `paper_id`：来源论文ID（对应 `knowledge_graph/nodes/papers.json` 中的记录）
- `section`：原文章节标题
- `paragraph_snippet`：原文片段（≥20字，直接引用，禁止改写）
- `score`：语义相似度分值

**无法找到原文片段支撑的结论必须标注 `evidence: unverified`，不得作为最终结论输出。**

## Key Rules

- **聚类依据必须是「去专有名词后的核心操作逻辑 + 共享假设」**，不得以模型名称（如「基于 GPT-4 的方法」）作为范式区分依据。
- 若某论文同时属于多个元范式，必须归为「混合架构」，不得强行拆分归入单一范式。
- 元范式命名必须使用文献中实际出现过的术语（如「基于变异测试」），不得纯由 LLM 造词。
- 孤立范式（仅 1 篇论文）必须标注 `single_paper_paradigm: true`，不得与多论文支撑的范式等权对待。
- 谱系树中的「替代」关系必须有时间证据（后出现的论文明确批评并替代前一范式）AND 存在 `contradicts` 边或明确否定性文本，不得基于逻辑推测声称替代关系。
- **认知坐标规则**：每次执行必须在 Checkpoint Output 的第一行记录认知坐标，格式为 `[认知坐标: S2.1 · 去名称化核心逻辑提取 · <本次执行的具体聚类策略>]`，用于追踪分析视角的一致性。
