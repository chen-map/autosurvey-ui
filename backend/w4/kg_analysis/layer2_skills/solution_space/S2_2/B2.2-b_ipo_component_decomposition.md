# Skill: B2.2-b 输入-处理-输出组件拆解

**层级**：S2.2 实现机制层 · Implementation & Adaptation  
**RQ类型**：具体怎么落地？（输入/输出 / 集成方式）  
**元认知逻辑**：将复杂解法还原为数据流管道，以「输入数据形态 → 核心处理逻辑 → 输出结果形态」三元组精确描述每个方法，并标注外部工具集成点，揭示方法的技术生态位。核心分析不在于枚举 I/P/O 内容，而在于分析每个边界点发生了什么信息转换、什么信息丢失——这才是方法局限性的根源。  
**认知基准面**：每个 I→P 和 P→O 边界都是信息损耗点——输入到处理的边界决定了「什么信息被纳入决策」，处理到输出的边界决定了「什么信息被压缩或丢弃」；方法的根本限制往往不在算法本身，而在边界处的信息损耗结构。

---

## Goal

对 KG 中每个解法方法，执行 IPO（Input-Process-Output）拆解，生成精确的数据流描述，揭示不同方法在输入表示、处理范式、输出格式上的系统性差异，并重点分析 I→P 和 P→O 边界的信息损耗。

---

## Inputs

- `knowledge_graph/nodes/methods.json` — KG 方法节点
- `paper_cards/parsed/` — Paper Cards，提取 Method / Implementation 章节
- `analyze_report/design_report.md` — RQ 定义

---

## Execution Steps

### Step 1: 通过 KG 边识别输入（硬需求 + 隐性输入）

**推理目标**：为什么区分「硬需求输入」和「隐性输入」？因为硬需求输入是方法无法运行的前提，而隐性输入（如预训练知识、标注数据）是方法真实成本的一部分，后者常被论文刻意淡化，但对于可复现性和迁移性至关重要。

**操作流程**：

首先通过 `requires` 边获取硬需求：
```python
for method in all_methods:
    hard_requirements = get_tail_entity(loader, "requires", method["node_id"])
    # hard_requirements 包含 assumption 和 dataset 节点
    # 其 canonical_name 描述了方法运行的前提条件
```

然后通过 paper 搜索发现隐性输入（论文中提及但未在 KG 中建模的输入依赖）：
```python
implicit_input_snippets = search_paper_sections(
    paper_cards_root="paper_cards/parsed",
    query="takes as input|given a|requires|we assume|our method needs|pre-trained on",
    paper_ids=[method["context_paper_id"]],
    topk=3
)
```

对比 KG `requires` 边列出的依赖和 paper 搜索发现的依赖：若 paper 中提及的依赖未出现在 KG `requires` 边中，标记为「隐性输入」，这往往是 KG 建模遗漏的依赖。

输入精度要求：必须区分：
- 代码序列（token stream）vs AST vs CFG vs PDG vs 字节码 — 不得笼统称为「代码」
- 自然语言文本 vs 结构化规范 vs 半结构化注释
- 原始输入 vs 预处理后的表示（如 embedding）

### Step 2: 通过论文搜索识别处理逻辑

**推理目标**：处理逻辑的识别目标不是罗列算法名称，而是提取「核心变换操作」——方法在做什么类型的计算？是在优化一个目标函数？在遍历一个状态空间？在匹配一个模式？这个计算类型才是方法的根本特征。

**操作流程**：

搜索 Paper Card 中描述核心算法步骤的段落：
```python
process_snippets = search_paper_sections(
    paper_cards_root="paper_cards/parsed",
    query="the algorithm|the model then|we first|processing step|our method applies|the key computation",
    paper_ids=[method["context_paper_id"]],
    topk=3
)
```

从搜索结果中提取：
1. 核心算法类别（如：Transformer 推理 / 图神经网络传播 / 约束求解 / 动态符号执行 / 进化搜索）
2. 关键处理步骤序列（步骤 1 → 步骤 2 → ...）
3. 是否存在迭代/循环结构（影响计算复杂度）

**外部依赖检测**：扫描 `description` 字段和处理步骤描述，找出所有命名工具/模型/服务。对每个命名实体，检查其是否在 KG 中存在对应节点：
```python
# 若某工具名在 KG 中无对应节点，它是外部依赖
external_tools = [tool for tool in named_entities_in_description
                  if not exists_in_kg(loader, tool)]
```
外部依赖是集成风险点，需标注版本锁定风险和可替换性。

### Step 3: 通过 `measured_by` 边识别输出

**推理目标**：为什么通过 `measured_by` 边推断输出，而不只是读论文的「输出」章节？因为度量指标揭示了输出的可测量属性——一个方法「输出什么」可以从「什么被度量」反向推断，且 KG 中的 metric 节点是经过规范化的，比论文原文描述更一致。

**操作流程**：

```python
for method in all_methods:
    metrics = get_tail_entity(loader, "measured_by", method["node_id"])
    # metrics 的 canonical_name 揭示了输出的可量化属性
    # 例如：若 metric 是 "precision/recall"，输出是二分类结果
    # 若 metric 是 "BLEU score"，输出是自然语言文本
    # 若 metric 是 "execution time"，输出涉及可运行的代码/程序
```

从 metrics 推断输出类型：
- 精度类指标（Precision/Recall/F1）→ 输出是分类标签
- 相似度类指标（BLEU/CodeBLEU/Edit Distance）→ 输出是生成文本/代码
- 通过/失败类指标（Pass@k/Test Pass Rate）→ 输出是可执行代码
- 时间/资源类指标 → 输出有运行时行为

补充 paper 搜索以覆盖 KG 未建模的输出属性：
```python
output_snippets = search_paper_sections(
    paper_cards_root="paper_cards/parsed",
    query="outputs|produces|generates|returns|the result is",
    paper_ids=[method["context_paper_id"]],
    topk=2
)
```

### Step 4: 边界分析——信息损耗审计

**推理目标**：这是 IPO 分析的最高价值步骤。每个 I→P 边界都是「输入信息被选择性纳入处理」的决策点，每个 P→O 边界都是「处理结果被压缩为输出表示」的决策点。在这些边界处丢失的信息，正是方法无法处理的场景——即方法的内在局限性。

**I→P 边界分析**：
- 输入是代码序列但处理是 GNN → 必须有「代码解析为图」的转换步骤 → 若解析器不支持某语言特性，该特性就是盲区
- 输入是自然语言但处理需要结构化信息 → 必须有「NL→结构化」的转换 → 解析错误率是误差来源

**P→O 边界分析**：
- 处理生成了丰富的中间表示，但输出只有二分类标签 → 压缩过程丢弃了不确定性信息 → 无法区分「确定不是问题」和「不确定是否是问题」
- 处理是概率模型，但输出是确定性决策 → 阈值选择影响最终结果

将边界分析结果与 KG 中的 `has_limitation` 边对比验证：
```python
method_limitations = get_tail_entity(loader, "has_limitation", method["node_id"])
# 若某 limitation 节点的描述对应某个边界损耗，则验证通过
# 若发现新的边界损耗未被 KG limitation 节点覆盖，标注为「新发现的隐性局限」
```

### Step 5: 生成 IPO 对比表与适配规律分析

构建「论文 × IPO 维度」对比表，对比所有方法的：
- 输入表示类型分布
- 处理算法类别分布
- 输出格式分布
- 外部工具依赖数量

分析输入类型与处理算法之间的关联规律（需有统计支撑，如「75% 的图结构输入方法使用 GNN 处理」）。

### Step 6: 对抗性验证——隐性假设暴露

**推理目标**：IPO 描述的最大盲区是「隐性假设」——方法在 I→P 边界上对输入做了哪些假设，但论文未明确声明？这些未声明的假设是方法泛化性的主要威胁。

**操作流程**：
- 对每个方法，从 `requires` 边的 assumption 节点中找出涉及输入格式的假设
- 搜索论文中的限制声明：
```python
assumption_snippets = search_paper_sections(
    paper_cards_root="paper_cards/parsed",
    query="we assume|limited to|only supports|requires that|cannot handle",
    paper_ids=[method["context_paper_id"]],
    topk=3
)
```
- 对比 assumption 节点和搜索结果，找出「KG 中未建模但论文中隐含」的假设，标注为 `implicit_assumption`

### Step 7: 原文溯源验证

对所有分析结论中引用的证据，使用 `search_paper_sections` 工具在 `paper_cards/parsed/` 中精确定位原文片段：

```python
snippets = search_paper_sections(
    paper_cards_root="paper_cards/parsed",
    query="<分析结论的关键词>",
    paper_ids=[<涉及的paper_id列表>],
    topk=3
)
```

每条关键结论必须附带：
- `paper_id`：来源论文ID
- `section`：原文章节标题
- `paragraph_snippet`：原文片段（≥20字，直接引用，禁止改写）
- `score`：语义相似度分值

**无法找到原文片段支撑的结论必须标注 `evidence: unverified`，不得作为最终结论输出。**

## Key Rules

- **IPO 描述精确度要求**：输入类型必须区分「代码序列」vs「AST」vs「CFG」vs「PDG」等不同表示，不得笼统称为「代码」。
- 外部工具集成点必须区分「硬依赖」（缺少该工具方法无法运行）和「软依赖」（可选增强），不得混淆。
- 若某论文的 Method 章节未明确描述输入格式，标注 `input_type: unspecified`，禁止推断填充。
- **边界损耗分析是必选步骤**，不得跳过——每个方法的 I→P 和 P→O 边界都必须有明确的信息损耗描述，即使是「无损耗」也需要明确声明并给出理由。
- IPO 适配规律声明需有统计数据支撑（如「75% 的图输入方法使用 GNN 处理」），不得仅凭少数案例泛化。
- 输出格式为「自然语言解释」的方法需特别标注，因其输出难以机器评估，这是一个质量评估维度。
- `measured_by` 边的 metric 节点是输出类型推断的主要来源；若 `measured_by` 边为空，从 paper 搜索补充，并标注 `output_inferred_from: paper_text`。
- **认知坐标规则**：每次执行在 Checkpoint Output 第一行记录认知坐标，格式为 `[认知坐标: S2.2 · IPO数据流解剖 · <本次分析的方法集合和重点边界类型>]`。
