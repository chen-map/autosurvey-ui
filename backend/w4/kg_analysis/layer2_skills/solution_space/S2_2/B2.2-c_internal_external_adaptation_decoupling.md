# Skill: B2.2-c 内外部适应机制解耦

**层级**：S2.2 实现机制层 · Implementation & Adaptation  
**RQ类型**：具体怎么落地？（干预深度分析）  
**元认知逻辑**：根据「内部干预程度」（对系统/模型内部参数的修改程度）和「外部增强程度」（对外部资源/工具的依赖程度）将适配策略分为不同层级，揭示设计选择在「轻量-重量」光谱上的分布规律。  
**认知基准面**：内部适配和外部适配的权衡不是效果问题，而是成本结构问题——内部适配把成本前置（训练时成本高，推理时自包含），外部适配把成本分散（训练简单，但运行时依赖外部服务的可用性和延迟）；真正的分析价值在于揭示每种适配策略的成本-风险结构，而不仅仅是给方法贴标签。

---

## Goal

将 KG 中的方法/解法按「内部干预度」和「外部依赖度」两个维度分类，建立四象限适配策略分布图，通过 KG 边结构（`relaxes`、`requires`、`has_limitation`）提取适配策略的代价-收益结构，揭示设计甜点与适配陷阱。

---

## Inputs

- `knowledge_graph/nodes/methods.json` — KG 方法节点，含 `adaptation_type` 属性（若有）
- `paper_cards/parsed/` — Paper Cards，提取 Method 章节的技术细节
- `working_memory/rq_{id}/B2.2-a_architecture_alignment_report.json`（可选）— 架构对齐结果
- `working_memory/rq_{id}/B2.2-b_ipo_report.json`（可选）— IPO 拆解结果

---

## Execution Steps

### Step 1: 通过 KG 边识别内部适配类型

**推理目标**：为什么用 `relaxes` 边识别内部适配？因为内部适配的本质是「放宽了对模型架构或训练数据的某些约束」——若一个方法 `relaxes` 了涉及「模型架构固定」或「参数不可修改」的 assumption 节点，它就是在进行内部干预。这比从论文文本中抽取微调方法名称更系统可靠。

**操作流程**：

```python
for method in all_methods:
    relaxed_assumptions = get_tail_entity(loader, "relaxes", method["node_id"])
    # 过滤涉及模型架构或训练数据的 assumption
    architecture_relaxations = [a for a in relaxed_assumptions
                                  if any(kw in a["canonical_name"].lower()
                                         for kw in ["model architecture", "parameter", "weight",
                                                    "training", "fine-tun", "frozen"])]
```

若 `relaxes` 边指向架构相关假设 → 内部适配信号（级别待定）

进一步从 Paper Card 确认具体的内部干预级别：
```python
internal_adaptation_snippets = search_paper_sections(
    paper_cards_root="paper_cards/parsed",
    query="fine-tuning|LoRA|adapter|full fine-tune|architecture modification|attention|layer|frozen|pre-trained",
    paper_ids=[method["context_paper_id"]],
    topk=3
)
```

内部干预级别（L）定义：
- **L0**：黑盒调用（零参数修改，仅 prompt 工程）
- **L1**：轻量适配（LoRA、适配器插件、few-shot）
- **L2**：部分微调（选择性层解冻微调）
- **L3**：全量微调（重新训练所有参数）
- **L4**：架构改造（修改模型结构本身——注意力机制、层数、激活函数；仅改变训练数据不算 L4）

**决策条件**：若论文 Method 章节未明确说明微调方式，标注 `internal_level: unspecified`，不得推断。

### Step 2: 通过 `requires` 边识别外部依赖类型

**推理目标**：外部依赖的关键特征是「运行时依赖外部系统的可用性」——`requires` 边指向外部工具/API/知识库的方法，其外部增强程度由依赖的外部节点数量和类型决定。这与 B2.2-b 的外部工具识别形成交叉验证。

**操作流程**：

```python
for method in all_methods:
    required_entities = get_tail_entity(loader, "requires", method["node_id"])
    # 过滤出外部工具/API 类型的依赖节点
    external_deps = [e for e in required_entities
                     if e["label"] in ["tool", "api", "database", "service"]]
```

同时，与 B2.2-b 的外部工具列表对比（若已执行），补充 KG 未建模的外部依赖。

外部增强级别（E）定义：
- **E0**：自包含（无外部依赖）
- **E1**：工具辅助（调用单一确定性工具，如静态分析器）
- **E2**：知识增强（依赖外部知识库/向量库）
- **E3**：多工具编排（协调多个外部系统）
- **E4**：人机协同（依赖人类反馈/标注）

混合策略处理：若方法同时使用多种外部依赖类型（如 LoRA + RAG），记录所有策略，取最高级别的 L 和 E 值，同时在 `adaptation_details` 字段记录所有组合。

### Step 3: 构建四象限分布图

以 L（内部干预，0~4）为纵轴、E（外部增强，0~4）为横轴，将所有方法投影到二维空间：

- **象限 I**（L ≤ 1, E ≤ 1）：轻量即插即用型 — 低风险、低成本、低定制化
- **象限 II**（L ≤ 1, E ≥ 2）：工具增强型 — 依赖外部服务，灵活但有运行时风险
- **象限 III**（L ≥ 2, E ≤ 1）：端到端深度定制型 — 高训练成本，运行时自包含
- **象限 IV**（L ≥ 2, E ≥ 2）：重量级混合型 — 最高成本，最高灵活性，最高风险

### Step 4: 用 `has_limitation` 边提取各象限的代价-风险结构

**推理目标**：四象限分类只是分布描述；真正的洞察在于每个象限的「局限性模式」——内部适配方法和外部适配方法的局限性是结构性不同的，不是程度差异而是类型差异。`has_limitation` 边提供了 KG 中对方法局限性的系统性编码。

**操作流程**：

```python
for method in all_methods:
    limitations = get_tail_entity(loader, "has_limitation", method["node_id"])
    # 按象限分组，统计各象限的局限性类型分布
```

内部适配局限性模式（L ≥ 2）：
- 数据需求：需要大量标注数据
- 计算成本：训练/微调的 GPU 资源消耗
- 泛化风险：对训练分布外的场景性能下降
- 更新成本：模型更新需要重新训练

外部适配局限性模式（E ≥ 2）：
- 可用性依赖：外部服务宕机时方法失效
- 延迟开销：调用外部 API 的额外延迟
- 隐私风险：数据需发送至外部服务
- 版本漂移：外部服务更新可能导致行为变化

对每种局限性类型，验证 KG `has_limitation` 边的覆盖情况：
```python
limitation_coverage = search_paper_sections(
    paper_cards_root="paper_cards/parsed",
    query="limitation|drawback|cannot|fails when|requires large|privacy|latency",
    paper_ids=[method["context_paper_id"]],
    topk=2
)
```

若 paper 中提及的局限性未出现在 `has_limitation` 边中，标注为「KG 未建模的局限性」。

### Step 5: 识别设计甜点

**推理目标**：设计甜点是效果与成本（综合训练成本+运行时成本+风险）的帕累托最优区域，需要同时考虑两个维度，不得仅凭效果最好或成本最低就声称为甜点。

**分析逻辑**：
- 若 B2.6-a 已执行，使用其成本数据；若无成本数据，标注 `cost_data: unavailable`
- 对每个象限，统计其 `has_limitation` 边的局限性严重程度分布
- 若某象限的方法数量多（> 30% 的总方法数）且局限性节点密度低（平均 `has_limitation` 边数少），该象限是设计甜点候选区
- 最终甜点判断需结合效果数据（来自 B2.3 系列）和成本数据，两者均需有文献支撑

### Step 6: 对抗性验证——适配策略稳健性检验

**推理目标**：一个适配策略在单一数据集上表现好不代表它稳健——需要检验该策略在其 `has_limitation` 边所描述的边界条件下是否真的失效。

**操作流程**：
- 对每个象限的代表性方法，找出其所有 `has_limitation` 节点描述的失效场景
- 搜索是否有其他论文在这些失效场景中对该方法进行了测试：
```python
failure_mode_test = search_paper_sections(
    paper_cards_root="paper_cards/parsed",
    query="<method_name> fails|<method_name> cannot handle|<method_name> limited to",
    paper_ids=all_paper_ids,
    topk=3
)
```
- 若找到失效验证证据，在输出中标注 `failure_verified: true`；若无验证，标注 `failure_tested: false`，该方法的局限性声明仅为理论预测

### Step 7: 原文溯源验证

对所有分析结论中引用的证据，使用 `search_paper_sections` 工具在 `paper_cards/parsed/` 中精确定位原文片段：

```python
snippets = search_paper_sections(
    paper_cards_root="paper_cards/parsed",
    query="<分析结论的关键词>",
    paper_ids=[<涉及的paper_id列表>],
    topk=3
)
```

每条关键结论必须附带：
- `paper_id`：来源论文ID
- `section`：原文章节标题
- `paragraph_snippet`：原文片段（≥20字，直接引用，禁止改写）
- `score`：语义相似度分值

**无法找到原文片段支撑的结论必须标注 `evidence: unverified`，不得作为最终结论输出。**

## Key Rules

- **L 和 E 级别的评定必须基于论文 Method 章节的具体技术描述**，若论文未明确说明微调方式，标注 `level: unspecified`，不得推断。
- L4（架构改造）需严格界定：必须是对模型结构本身（如注意力机制、层数、激活函数）做了修改，仅改变训练数据不算 L4。
- **`relaxes` 边是内部适配信号的主要 KG 来源**，必须在评级前检查；`relaxes` 边指向架构相关假设是 L ≥ 2 的充分条件。
- `requires` 边指向外部工具/API 节点是外部依赖的主要 KG 来源；未在 KG 中建模的外部依赖需从 paper 文本中补充，并标注 `dep_source: paper_text`。
- 效果-成本分析只能基于 B2.6-a 已提取的显式成本数据，若无成本数据，标注 `cost_data: unavailable`，不得估算。
- 「设计甜点」识别需同时考虑效果和成本两个维度，不得仅凭效果最好或成本最低就声称为甜点。
- 若某方法采用了混合策略（如同时使用 LoRA + RAG），需记录所有策略，取最高级别的 L 和 E 值。
- **认知坐标规则**：每次执行在 Checkpoint Output 第一行记录认知坐标，格式为 `[认知坐标: S2.2 · 内外部适配代价-风险结构解耦 · <本次分析的方法集合和象限重点>]`。
