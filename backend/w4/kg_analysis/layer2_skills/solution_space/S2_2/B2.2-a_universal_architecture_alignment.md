# Skill: B2.2-a 通用架构对齐与参数化

**层级**：S2.2 实现机制层 · Implementation & Adaptation  
**RQ类型**：具体怎么落地？（适配策略）  
**元认知逻辑**：提取所有方法共享的底层事件序列，定义「超模型」骨架，将每篇论文的方法视为骨架中各组件的不同参数配置，通过横向对比揭示设计选择的多样性与设计空间。  
**认知基准面**：通用骨架的价值不在于描述所有方法「都做什么」，而在于揭示哪些组件是设计自由度最高的变异点——高变异组件才是创新发生的地方，低变异组件是领域共识的体现。

---

## Goal

从 KG 和 Paper Cards 中提取所有解法共享的通用流水线骨架（N 个组件），将每个具体方法映射为骨架中各组件的配置参数，生成可横向对比的「方法配置表」。

---

## Inputs

- `knowledge_graph/nodes/methods.json` — KG 方法节点
- `paper_cards/parsed/` — Paper Cards，提取 Method 章节的架构描述
- `working_memory/rq_{id}/B2.1-a_paradigm_report.json` — 元范式分类（同一范式内才适合对齐）
- `analyze_report/design_report.md` — RQ 定义

---

## Execution Steps

### Step 1: 通过高频结构搜索提取通用骨架

**推理目标**：为什么用「高频组件」而非「理想化组件」定义骨架？因为如果骨架包含文献中不存在的组件，对齐就会产生大量虚假的 `not_applicable` 标注，骨架就失去意义。只有在 ≥70% 的方法中出现的结构性组件，才有资格成为通用骨架的一部分。

**操作流程**：

搜索论文中描述系统整体结构的段落，这些段落通常描述了流水线的完整阶段：
```python
pipeline_overview_snippets = search_paper_sections(
    paper_cards_root="paper_cards/parsed",
    query="pipeline consists of|our system has|architecture overview|framework has|our approach involves|the following stages",
    topk=15
)
```

从这些段落中提取阶段名称和组件描述，统计每个结构性组件在多少篇论文中出现。只有出现频率 ≥ 70% 的组件才纳入通用骨架。

同时，利用 KG 结构作为交叉验证：
- `requires` 边的尾节点揭示了方法的输入需求 = 流水线入口条件
- `measured_by` 边的尾节点揭示了方法产生的可测量输出 = 流水线出口特征

```python
for method in all_methods:
    pipeline_inputs = get_tail_entity(loader, "requires", method["node_id"])
    pipeline_outputs = get_tail_entity(loader, "measured_by", method["node_id"])
    # pipeline_inputs 的 canonical_name 集合 = 该方法需要的前置数据
    # pipeline_outputs 的 canonical_name 集合 = 该方法产生的可量化结果
```

**决策条件**：若超过 30% 的方法在某候选组件上标记 `not_applicable`，该组件不得纳入通用骨架，而应降格为「可选扩展组件」。

### Step 2: 将每个方法映射为骨架组件配置

**推理目标**：映射的目的不是为了描述方法「有什么」，而是为了揭示方法「在哪里做了不同的选择」。因此，关键是识别每个组件上的配置多样性，而不是简单地记录实现名称。

**操作流程**：

对每个 KG Method 节点，从 Paper Card 中提取其在每个骨架组件上的具体实现：
```python
for method in all_methods:
    paper_id = method["context_paper_id"]
    # 搜索该方法对每个骨架组件的具体实现描述
    for component in universal_skeleton:
        component_impl = search_paper_sections(
            paper_cards_root="paper_cards/parsed",
            query=component["search_keywords"],
            paper_ids=[paper_id],
            topk=2
        )
```

同时，检查 `relaxes` 边——若方法有 `relaxes` 边指向某 assumption 节点，该 assumption 所描述的约束对应的骨架组件可能被该方法「绕过」或「简化」，这是 `omitted` vs `not_applicable` 的关键区分依据：
```python
relaxed_assumptions = get_tail_entity(loader, "relaxes", method["node_id"])
# 若 relaxed_assumptions 中包含某骨架组件的前提假设，
# 则该方法可能省略了该组件（omitted），而非该组件不适用（not_applicable）
```

**状态标注规则**：
- `standard`：使用了该组件的主流实现方式
- `novel`：论文明确声称对该组件的实现有创新（需从 `novelty_claim` 字段或 paper 的 contribution 描述中验证）
- `omitted`：该组件概念适用，但论文未讨论其实现（需标注原因）
- `not_applicable`：该组件在此论文的任务场景中概念上不适用（需说明为何不适用）

若某 Paper Card 的 Method 章节描述少于 200 字，标注 `method_detail: insufficient`，对应组件不得推断填充。

### Step 3: 生成方法配置对比表

构建「论文 × 组件」对比表，每个单元格记录该论文在该组件的具体实现状态：

| 论文 | 组件1 | 组件2 | ... | 组件N |
|------|-------|-------|-----|-------|
| P1   | standard: RNN | novel: hierarchical BFS | ... | omitted |

每个非 `not_applicable` 和非 `omitted` 的单元格都必须有对应的 `paragraph_snippet` 作为证据。

### Step 4: 识别变异维度（设计热点）与约束维度（设计共识）

**推理目标**：高变异组件是创新焦点，但「低变异组件」同样重要——它们揭示了领域的设计共识，即「该步骤的实现方式已被社区收敛到某种标准形态」。识别两者同样有分析价值。

统计每个组件的配置多样性（不同配置数 / 非omitted/not_applicable 的论文数）：
- 多样性得分 > 0.6 = 高变异组件（设计热点）
- 多样性得分 < 0.3 = 低变异组件（设计共识）

对「设计共识」组件，分析其收敛的实现方式，并用 `search_paper_sections` 验证该标准实现在文献中的普遍性。

### Step 5: 识别组件间设计协同与约束关系

分析是否存在「若选择组件 A 的方案 X，则往往选择组件 B 的方案 Y」的共现关系：
```python
# 计算 (组件A=方案X, 组件B=方案Y) 的共现率
co_occurrence_rate = count(papers where A==X and B==Y) / count(papers where A==X)
# co_occurrence_rate > 0.7 = 强协同关系
```

对「不兼容」声明（某两个组件配置不能共存），必须有理论依据或文献实验证据，不得仅凭统计上的低共现率推断不兼容。

`relaxes` 边指向的 assumption 节点也揭示了隐性约束：若两个方法都 `relaxes` 同一个假设，它们在该组件上很可能采用了类似的策略。

### Step 6: 对抗性验证——骨架完备性自检

**推理目标**：通用骨架定义完成后，必须问一个反向问题：「有没有重要的实现差异被骨架遗漏了？」——即某些创新不体现在骨架的任何组件上，而是在组件之间的连接方式或整体协调机制上。

**操作流程**：
- 对每篇论文的 contribution 声明，检查其是否能被完整映射到骨架的某个组件
- 若某论文的主要贡献无法归入任何骨架组件（映射失败），这说明骨架存在结构性缺失，需要新增组件或重新划分组件边界
- 记录映射失败的论文和其贡献描述，作为骨架修订的依据

### Step 7: 原文溯源验证

对所有分析结论中引用的证据，使用 `search_paper_sections` 工具在 `paper_cards/parsed/` 中精确定位原文片段：

```python
snippets = search_paper_sections(
    paper_cards_root="paper_cards/parsed",
    query="<分析结论的关键词>",
    paper_ids=[<涉及的paper_id列表>],
    topk=3
)
```

每条关键结论必须附带：
- `paper_id`：来源论文ID
- `section`：原文章节标题
- `paragraph_snippet`：原文片段（≥20字，直接引用，禁止改写）
- `score`：语义相似度分值

**无法找到原文片段支撑的结论必须标注 `evidence: unverified`，不得作为最终结论输出。**

## Key Rules

- **通用骨架的定义必须基于文献集中实际存在的方法组件**，且覆盖率 ≥ 70% 才能成为强制组件；覆盖率 30%~70% 的组件降格为可选扩展组件；< 30% 的组件不纳入骨架。
- `status: omitted` 和 `status: not_applicable` 需区分：omitted 表示该组件存在但论文未讨论；not_applicable 表示该组件概念在此论文的任务场景中不适用。
- 设计关联分析中的「不兼容」声明需有理论依据或文献实验证据，不得仅凭统计上的低共现率推断不兼容。
- 若某 Paper Card 的 Method 章节描述过于简略（< 200 字），标注 `method_detail: insufficient`，对应配置项不得推断填充。
- 骨架定义后必须执行完备性自检：若超过 5% 的论文贡献无法映射到任何骨架组件，必须修订骨架后再输出。
- `relaxes` 边指向的 assumption 是组件省略的重要解释来源，必须在配置标注中引用。
- **认知坐标规则**：每次执行在 Checkpoint Output 第一行记录认知坐标，格式为 `[认知坐标: S2.2 · IPO数据流解剖 · <本次分析的骨架版本和覆盖论文数>]`。
