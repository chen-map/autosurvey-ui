# Skill: B2.5-b 信任缺口与治理需求分析

**层级**：S2.5 成熟演进层 · Maturity & Engineering Challenges  
**RQ类型**：离实用多远？（可解释/可信）  
**元认知逻辑**：分析方案从实验室到规模化部署后暴露的「信任真空」，推导弥补信任缺口所需的「治理原语」（如沙箱隔离、审计机制、访问控制），评估当前方案是否具备规模化所需的信任工程基础。  
**认知基准面**：信任缺口不是安全漏洞列表——它是「在规模化条件下哪些假设会失效」的结构性分析；assumption 节点中涉及信任、安全、合规的，就是需要治理干预的信任依赖点。

---

## Goal

识别 Solution Space 中各方案在规模化后暴露的信任缺口（安全性/可解释性/合规性维度），推导填补缺口所需的治理原语，评估当前方案的信任工程成熟度，量化有多少必要的治理原语已被实现。

---

## Inputs

- `knowledge_graph/nodes/methods.json` — KG 方法节点
- `knowledge_graph/nodes/assumptions.json` — KG assumption 节点（信任依赖的结构化来源）
- `paper_cards/parsed/` — Paper Cards，提取 Security / Privacy / Limitation / Deployment 章节
- `working_memory/rq_{id}/A1.6-b_problem_shift_report.json` — 次生灾害清单（关联信任风险）
- `working_memory/rq_{id}/B2.5-a_evidence_chain_report.json` — 工业就绪度评估

## Execution Steps

### Step 1: 从 KG assumption 节点识别信任依赖（结构化来源优先）

**为什么这样做**：信任缺口不应该靠分析者「想到什么安全问题」来发现，而应该从 KG 的 assumption 节点中找——这些是方法成立所依赖的前提条件，当规模化打破这些前提时，信任缺口就暴露了。

```python
all_assumptions = get_entity_by_type(loader, "assumption")

# 筛选涉及信任、安全、合规的 assumption 节点
trust_assumptions = []
trust_keywords = ["trust", "security", "compliance", "privacy", "auditability",
                  "explainability", "access control", "authentication", "authorization"]
for assumption in all_assumptions:
    desc = assumption.get("description", "").lower()
    name = assumption.get("name", "").lower()
    if any(kw in desc or kw in name for kw in trust_keywords):
        trust_assumptions.append(assumption)
        # 找到依赖该信任假设的方法
        dependent_methods = get_head_entity(loader, "requires", assumption["id"])
        assumption["trust_dependent_methods"] = [m["id"] for m in dependent_methods]
```

从 `trust_assumptions` 出发，构建「信任依赖图谱」：哪些方法依赖哪些信任前提，一旦前提在规模化后失效，就暴露了对应的信任缺口。

**信任缺口的分析必须基于文献中明确讨论的 Security/Privacy threats，不得凭空构造信任风险。**

### Step 2: 识别规模化暴露的信任缺口（文本证据补充）

**为什么这样做**：KG assumption 节点给出了静态的信任依赖，但规模化后的新问题往往体现在论文的 Future Work 和 Deployment 章节——这些是动态暴露的缺口，需要通过全文搜索补充。

```python
# 规模化后的信任压力点
scale_trust_evidence = search_paper_sections(
    paper_cards_root="paper_cards/parsed",
    query="at scale|when deployed widely|in production trust security concern|scalability concern",
    topk=10
)

# 信任失效的具体描述
trust_failure_evidence = search_paper_sections(
    paper_cards_root="paper_cards/parsed",
    query="black box decision|unexplainable|audit trail|compliance requirement|adversarial attack",
    topk=10
)
```

对每个解法/解法集群，从 Paper Cards 的 Security / Limitation 章节，提取在各信任维度上明确讨论的缺口：
- 「该方法是黑盒决策，无法解释具体原因」→ 可解释性缺口
- 「该方法需要访问完整训练数据，存在隐私泄露风险」→ 隐私保护缺口

**信任维度框架**（依据研究领域选择 3~5 个）：
- **安全性**：方案本身能否被攻击/绕过？（结合 A1.6-b 次生灾害）
- **可解释性**：方案的决策过程是否对用户可理解？
- **可审计性**：方案的行为是否可被事后审查？
- **隐私保护**：方案运行是否需要访问用户敏感数据？
- **合规性**：方案是否符合相关法规（GDPR/FDA/NIST）？

### Step 3: 推导治理原语（逻辑链驱动，非名词堆砌）

**为什么这样做**：推导治理原语不是「列举流行安全技术」，而是对每个信任缺口推导：「缺口的本质是什么 → 什么机制可以弥补这个本质缺陷 → 具体实现是什么」。没有这个逻辑链，治理原语只是空洞的词汇。

对每个信任缺口，按「缺口本质 → 治理逻辑 → 治理原语」推导：

```
可解释性缺口：
  缺口本质：模型决策依赖高维特征，人类无法直觉理解
  治理逻辑：需要将决策映射到人类可理解的概念空间
  治理原语：局部解释机制（LIME/SHAP）、规则提取

可审计性缺口：
  缺口本质：行为发生后无法追溯决策过程
  治理逻辑：需要不可篡改的行为记录
  治理原语：不可变审计日志、行为快照

安全性缺口：
  缺口本质：对抗输入可绕过检测
  治理逻辑：需要在决策边界外增加防护层
  治理原语：沙箱隔离、输入过滤、对抗训练

隐私缺口：
  缺口本质：训练/推理依赖原始敏感数据
  治理逻辑：需要在不访问原始数据的条件下完成计算
  治理原语：差分隐私、联邦学习、数据最小化

合规缺口：
  缺口本质：行为不符合法规要求的可追责性
  治理逻辑：需要行为符合法规约束并可证明
  治理原语：认证流程、合规性检查清单
```

**合规性缺口分析只能基于文献中明确引用的法规/标准**（如论文中提到 GDPR 要求），不得引入文献未讨论的监管框架。

### Step 4: 量化治理集成度（通过 KG addresses 边衡量）

**为什么这样做**：评估「当前方案是否具备信任工程基础」不能靠主观印象，必须用 KG 中「有多少方法已经实现了所需的治理原语」来量化——这将每个治理原语需求转化为一个 KG 中可查询的 problem 节点。

```python
for governance_requirement in required_governance_primitives:
    # 将治理需求映射到 KG 的 problem 节点
    governance_problem_id = map_governance_to_problem(governance_requirement)

    if governance_problem_id:
        # 找到已经解决了该治理需求的方法
        addressing_methods = get_head_entity(loader, "addresses", governance_problem_id)
        governance_requirement["implementation_count"] = len(addressing_methods)

        if len(addressing_methods) >= 3:
            governance_requirement["maturity"] = "mature"
        elif len(addressing_methods) >= 1:
            governance_requirement["maturity"] = "emerging"
        else:
            governance_requirement["maturity"] = "absent"
```

信任成熟度评分：`mature` 治理原语数 / 总必要治理原语数 = 信任工程覆盖率。

### Step 5: 原文溯源验证

对所有分析结论中引用的证据，使用 `search_paper_sections` 工具在 `paper_cards/parsed/` 中精确定位原文片段：

```python
snippets = search_paper_sections(
    paper_cards_root="paper_cards/parsed",
    query="<分析结论的关键词>",
    paper_ids=[<涉及的paper_id列表>],
    topk=3
)
```

每条关键结论必须附带：
- `paper_id`：来源论文ID（对应 `knowledge_graph/nodes/papers.json` 中的记录）
- `section`：原文章节标题
- `paragraph_snippet`：原文片段（≥20字，直接引用，禁止改写）
- `score`：语义相似度分值

**无法找到原文片段支撑的结论必须标注 `evidence: unverified`，不得作为最终结论输出。**

## Key Rules

- **信任缺口必须基于文献中的 Security/Privacy/Limitation 章节**，不得由 LLM 凭通用安全知识构造缺口。
- 「高危」信任缺口必须与 A1.6-b 的次生灾害清单交叉验证，若某安全缺口在 A1.6-b 中已有记录，应标注关联。
- 治理原语的推导必须有逻辑链（「为什么该原语能填补该缺口」），不得简单列举流行技术名词。
- 合规性缺口分析只能基于文献中明确引用的法规/标准（如论文中提到 GDPR 要求），不得引入文献未讨论的监管框架。
- 治理集成度的「mature」标注需要 ≥ 3 篇论文已实现该集成，「emerging」需要 1~2 篇，「absent」表示无论文实现。
- **KG assumption 节点是信任依赖的主索引**：必须先执行 `get_entity_by_type(loader, "assumption")` 并筛选信任相关节点，再用文本搜索补充；不得跳过 KG 结构直接从文本列举安全问题。
- **认知坐标纪律**：本技能的核心产出是「哪些信任假设在规模化后会失效」以及「当前方案中有多少必要的治理原语已被实现」——信任工程覆盖率是最终核心数字，而非信任缺口数量。
