# Skill: A1.5-b 瓶颈/缺陷逆向映射

**层级**：P1.5 认知空白层 · Gaps & Unknowns  
**RQ类型**：还缺什么？（根本性障碍）  
**元认知逻辑**：不再分析单一 Problem 的局限性，而是横向汇总所有 Problem 节点研究中反复出现的「共性局限性」，聚类提炼为根本性硬约束，论证这些约束为何在当前技术范式下无法逾越。  
**认知基准面**：以「共享局限性的硬约束提炼」为透镜——被多个方法同时声明的局限性是基础性约束的信号；被一个方法独有的局限性通常是实现缺陷；「不可逾越性」不是声称而是论证，必须区分「工程上很难」（软约束）和「当前范式基本假设本身导致无法解决」（硬约束）。

---

## Goal

从前序分析层（P1.1~P1.4）和 Paper Cards 的 Limitation 章节，系统性收集所有「局限性」表述，通过语义聚类提炼 3~5 个底层硬约束，并为每个硬约束构建「不可逾越性论证」。

---

## Inputs

- `working_memory/rq_{id}/A1.3-b_painpoint_remedy_report.json` — 开放痛点列表（可选）
- `working_memory/rq_{id}/A1.4-b_evaluation_audit_report.json` — 评估偏差审计结果（可选）
- `working_memory/rq_{id}/A1.5-a_blindspot_report.json` — 盲区分析结果（可选）
- `paper_cards/parsed/` — Paper Cards，重点提取 Limitation / Future Work / Discussion 章节
- `knowledge_graph/nodes/problems.json` — KG Problem 节点

## Execution Steps

### Step 1: 收集全量局限性表述

**认知目标**：KG 的 `limitation` 节点是全量局限性的结构化存储——从这里出发比手动翻阅 Paper Cards 更完整，因为 KG 已经对论文中的局限性声明做了结构化编码。`get_entity_by_type(loader, "limitation")` 是此步的正确起点，而非全文搜索。

```python
# KG limitation 节点是真实存在的节点类型
all_limitations = get_entity_by_type(loader, "limitation")
# 每个 limitation 节点的 description 字段包含局限性的文本描述
# node_id, canonical_name, label, origin_paper_id 字段提供溯源信息
```

对每个 limitation 节点，若 `origin_paper_id` 为 null，调用 `get_evidence_papers(loader, limitation_id)` 获取支撑论文集：

```python
for limitation in all_limitations:
    if limitation.get("origin_paper_id") is None:
        supporting_papers = get_evidence_papers(loader, limitation["node_id"])
    else:
        supporting_papers = [limitation["origin_paper_id"]]
    limitation["resolved_papers"] = supporting_papers
```

同时，确认每个局限性被多少个不同方法节点共享：

```python
for limitation in all_limitations:
    limitation_id = limitation["node_id"]
    # 找到 has_limitation 边指向该 limitation 的所有方法节点
    methods_with_this_limitation = get_head_entity(loader, "has_limitation", limitation_id)
    limitation["shared_by_methods_count"] = len(methods_with_this_limitation)
    limitation["shared_by_methods"] = [m["node_id"] for m in methods_with_this_limitation]
```

**高共享度（≥3 个方法）的局限性节点是基础性约束的候选。**

补充：从 Paper Cards Limitation/Future Work 章节做全文搜索，捕获 KG 可能未收录的局限性声明：

```python
limitation_text_hits = search_paper_sections(
    paper_cards_root="paper_cards/parsed",
    query="our method is limited by we cannot handle",
    topk=10
)
```

**硬约束的总结必须追溯到具体的文献作者自述（Author claimed limitations），禁止 LLM 凭先验知识构造局限性。**

### Step 2: 语义聚类提炼共性局限性

**认知目标**：聚类的目的是找到「多个方法都面临的同一底层约束」，而非仅仅将相似描述合并。高共享度 limitation 节点（`shared_by_methods_count ≥ 3`）自然形成聚类核心——这是 KG 提供的结构化聚类信号，优先于纯文本语义聚类。

```python
# 按共享方法数量排序，高共享度节点优先作为聚类中心
sorted_limitations = sorted(
    all_limitations,
    key=lambda x: x["shared_by_methods_count"],
    reverse=True
)
# 取 top-N 作为聚类种子，将语义相近的局限性归入同一聚类
```

目标聚类数：3~5 个底层共性约束。每个聚类中至少包含 2 篇以上论文的局限性表述。

聚类数量强制控制在 3~5 个，若产生更多类，需手动合并（保留差异描述，不得强行同质化）。

### Step 3: 提炼根本性硬约束

**认知目标**：「硬约束」与「软约束」的区分标准不是「难度高低」，而是「是否根植于当前范式的基本假设」——如果改变范式（如从监督学习换到强化学习）能够消除该约束，则是软约束；如果该约束来自更基础的数学/物理/信息论限制，则是硬约束。这个区分必须给出明确判断标准。

对每个高频共性局限性聚类，分析其是否构成「硬约束」：
- **硬约束**：根植于当前技术范式的基本假设，只有换范式才能突破
- **软约束**：当前实现的工程局限，原则上可通过更好的工程解决

判断辅助：检索是否有论文声称突破了该约束但仍在相同范式内：

```python
for cluster in limitation_clusters:
    constraint_text = cluster["representative_description"]
    # 检索是否有人尝试突破该约束
    breakthrough_attempts = search_paper_sections(
        paper_cards_root="paper_cards/parsed",
        query=f"overcome {constraint_text[:60]} without",
        paper_ids=cluster["all_source_paper_ids"],
        topk=3
    )
```

若有突破尝试且成功（结果为正），该约束可能是软约束；若尝试均失败或无人尝试，硬约束的论断更有支撑。

### Step 4: 构建「不可逾越性论证」

**认知目标**：「不可逾越性论证」必须区分三种不同强度的主张：①「数学上已证明不可能」（最强，需要数学证明）；②「已有多次突破尝试均失败」（强，需要失败尝试的文献证据）；③「当前范式的基本假设决定了无法解决」（中，需要逻辑推理+文献支持）。绝大多数情况属于②或③，不得声称①。

使用文献检索验证不可逾越性：

```python
for hard_constraint in hard_constraints:
    # 检索「不可逾越」的直接证据
    inviolability_evidence = search_paper_sections(
        paper_cards_root="paper_cards/parsed",
        query="fundamental limitation cannot be overcome inherent constraint",
        paper_ids=hard_constraint["source_paper_ids"],
        topk=5
    )
    # 检索是否有人声称突破但实际未成功
    failed_breakthrough = search_paper_sections(
        paper_cards_root="paper_cards/parsed",
        query=f"{hard_constraint['name']} remains challenging despite",
        topk=3
    )
```

对每个硬约束，构建论证结构：
1. 该约束的物理/数学/计算本质是什么？（来自 limitation 节点 `description` + 文献原文）
2. 为什么改进工程实现无法消除该约束？（逻辑推理，需文献支撑）
3. 是否有论文尝试过突破该约束？结果如何？（来自 `breakthrough_attempts` 检索结果）

若无已有突破尝试的文献证据，明确说明「尚无文献尝试突破」，不得声称「已被证明不可能」。

### Step 5: 指向未来研究方向

**认知目标**：硬约束的价值不仅在于解释「为什么当前研究有上限」，更在于指向「突破这个约束需要什么样的范式变革」。每个硬约束应对应一个可操作的「范式变革需求」描述，供 RQ5 层使用。

每个硬约束对应一个「范式变革需求」，作为 RQ5（挑战与未来）的输入：
- 当前范式的核心假设是什么
- 打破该假设需要引入什么新的基础理论/技术路线
- 已有的探索方向（来自 Future Work 章节）

### Step 5a: 对抗性验证硬约束分类

**认知目标**：「硬约束」是强主张，在最终输出前必须反向检验：有无论文声称通过工程改进克服了该约束？若有，则应降级为软约束或标注「约束边界存在争议」。

```python
for hard_constraint in hard_constraints:
    # 检索是否有论文声称用工程方法克服了该约束
    engineering_fix_claims = search_paper_sections(
        paper_cards_root="paper_cards/parsed",
        query=f"address {hard_constraint['name']} by engineering optimization",
        topk=3
    )
    if engineering_fix_claims and max(s["score"] for s in engineering_fix_claims) > 0.7:
        hard_constraint["constraint_type_disputed"] = True
        hard_constraint["dispute_evidence"] = engineering_fix_claims[0]
        # 降级为软约束并标注争议
```

### Step 6: 原文溯源验证

对所有分析结论中引用的证据，使用 `search_paper_sections` 工具在 `paper_cards/parsed/` 中精确定位原文片段：

```python
snippets = search_paper_sections(
    paper_cards_root="paper_cards/parsed",
    query="<分析结论的关键词>",
    paper_ids=[<涉及的paper_id列表>],
    topk=3
)
```

每条关键结论必须附带：
- `paper_id`：来源论文ID（对应 `knowledge_graph/nodes/papers.json` 中的记录）
- `section`：原文章节标题
- `paragraph_snippet`：原文片段（≥20字，直接引用，禁止改写）
- `score`：语义相似度分值

**无法找到原文片段支撑的结论必须标注 `evidence: unverified`，不得作为最终结论输出。**

## Key Rules

- **局限性表述必须来自论文原文的 Limitation 章节**（作者自述），或 KG limitation 节点（已编码的作者自述）；引用段落必须包含来源 paper_id 和章节标识。
- 硬约束 vs 软约束的区分必须给出明确的判断标准，不得仅凭「这个问题很难」就标注为硬约束。
- 「不可逾越性论证」中若无已有突破尝试的文献证据，需明确说明「尚无文献尝试突破」，不得声称「已被证明不可能」。
- 聚类数量强制控制在 3~5 个，若聚类算法产生更多类，需手动合并直到满足约束，防止过细化分析。
- 若某局限性同时被多篇论文提及但各有细微差异，需在聚类时保留差异描述，不得强行同质化。
- **认知坐标纪律**：`get_entity_by_type(loader, "limitation")` + `get_head_entity(loader, "has_limitation", limitation_id)` 是局限性收集和共享度统计的客观方法，必须在文本检索之前优先执行。
